# §7.5 Search algorithm

Part of the [Wayfindr technical design](../design.md). Go code cites this file
as "design §7.5".

- **Tokenizer.** Lowercase the text. Split on non-alphanumerics, then on
  camelCase and digit boundaries. Drop tokens shorter than 2 characters.
  `createIssue`, `create_issue`, and `create-issue` all become
  `[create, issue]`.
- **Plural folding.** Each token of at least 4 characters is folded to a
  singular by the first matching suffix rule below. When folding changes an
  indexed token, the index keeps the token and adds the folded form after it, so
  `list_issues` becomes `[list, issues, issue]`. A singular query then matches a
  tool that only uses the plural.

  | Ending                | Rule             | Example                                    |
  | --------------------- | ---------------- | ------------------------------------------ |
  | `ies` (5+ characters) | replace with `y` | `queries` → `query`                        |
  | `ies` (4 characters)  | unchanged        | `ties`, `lies`                             |
  | `sses`                | drop `es`        | `classes` → `class`                        |
  | `xes`, `ches`, `shes` | drop `es`        | `indexes` → `index`, `branches` → `branch` |
  | `ss`, `us`, `is`      | unchanged        | `class`, `status`, `analysis`              |
  | `s`                   | drop `s`         | `invoices` → `invoice`                     |

  The rules are not a stemmer. They also fold third-person verbs (`shows` →
  `show`), and they miss some plurals (`statuses` → `statuse`, `caches` →
  `cach`).

- **Query words.** Queries are split and folded by the same rules, but each
  query word carries a total weight of 1. A word that folding changes splits
  that weight 0.5 / 0.5 between its surface and folded forms when the vocabulary
  has both, and gives all of it to whichever form is present otherwise. So a
  plural query word counts once, not twice, yet an exact plural
  (`workflow runs`, `thread replies`) still outranks a tool that only has the
  singular. Dropping the surface form from queries entirely was tried and lost
  three golden expectations that rely on it.
- **Lexical score (SQLite, in memory).** A BM25F variant (k1 = 1.2, b = 0.75)
  with field weights: qualified name 3.0, title 2.0, parameter names 1.5,
  description 1.0, parameter descriptions 0.5. Typo tolerance: a query word (at
  least 4 characters) with no exact match for its surface or folded form is
  expanded, from both forms, to vocabulary tokens whose trigram Jaccard
  similarity is at least 0.4. Those matches are weighted by their similarity.
  Trigrams cover every vocabulary token, surface plurals included, so `serie`
  still finds `series` even though `series` folds to `sery`. A match on a
  surface plural is scored as its folded form: a tool that has a plural also has
  its folded form, so scoring both would count the tool twice. A tool is a
  lexical candidate when its score is greater than 0.
- **Connector filter.** Collection statistics (document frequency, idf, and
  average field lengths) always come from the user's whole catalog. The
  `connectors` filter only skips results, so a filtered ranking equals the
  unfiltered ranking restricted to those connectors. With a query vector, the
  filter applies after fusion: both lists, and so both sets of ranks, come from
  the whole catalog.
- **Vector score.** Cosine similarity between the query vector and every tool
  vector with the query's model identity (`SearchQuery.ModelID`, the identity
  that embedded the query). The top 50 with a cosine above 0 are vector
  candidates, ordered by cosine, ties by qualified name. A tool vector of
  another length is skipped. Without a query vector there are no vector
  candidates.
- **Fusion.** Reciprocal-rank fusion (RRF): `score = Σ 1 / (5 + rank)` over the
  two lists, ranks counting from 1; a tool in only one list gets only that term.
  Ties are broken by qualified name, ascending. A lexical-only search fuses one
  list, which keeps its order, whatever the constant. A query with no lexical
  candidates returns the vector candidates alone. Pagination is an offset into
  the fused list, and `has_more = total > page × size`.
  - **Why k = 5.** The usual constant, 60, comes from fusing ranked runs of
    about 1,000 documents each, where the top few places should count little
    more than the next few. Here the vector list holds at most 50 tools and a
    page shows 5, so a tool one list puts first should outweigh one both lists
    put in the middle. With k = 60, a tool first in one list and absent from the
    other scores `1/61`, below any tool both lists place 61st or better, so a
    strong single-list hit (a meaning match whose words appear nowhere in the
    tool) rarely reaches the first page. With k = 5 it scores `1/6`, which ties
    a tool both lists place seventh (`2/12`) and beats one both place eighth or
    lower.
  - **How it was chosen.** On the golden fixture with `qwen3-embedding:0.6b`,
    every k tried from 1 to 12 met every expectation, and every k tried from 15
    to 60 missed one. On held-out vectors from `nomic-embed-text`, k = 5 cut the
    misses from 9 to 5. Normalized score fusion (min-max and mean ± 3σ, convex
    weights 0.3 to 0.7) broke expectations that RRF meets. A cosine floor that
    promotes the top vector hit depends on the model's similarity range, so it
    does not carry across models.
- **Exact-name boost.** A query that names a tool exactly ranks that tool ahead
  of every other result, lexical-only or hybrid. "Exactly" means the query's
  words equal the words of the tool's name or of its qualified name, in order,
  where words are the tokenizer's (split, lowercased, under 2 characters
  dropped) without plural folding. So `list issues`, `list_issues`,
  `listIssues`, and `List-Issues` name both `github.list_issues` and
  `linear.list_issues`; `github.list_issues` and `github list issues` name only
  the first. `list issue` (folded), `issues list` (order), and `list the issues`
  (an extra word) name neither. Folding stays out because a name is an
  identifier the user typed, and `list_issue` and `list_issues` can be different
  tools. Several exact matches keep their fused order among themselves; the rest
  follow in fused order. The fused score is not changed, and `Score.ExactName`
  says why a result leads. The boost exists because RRF only counts ranks: a
  tool whose name the user typed can sit second or third in both lists behind
  near neighbours (`get_issue` ahead of `get_issue_details`) and lose the fused
  first place it plainly deserves. It is applied after fusion and before the
  connector filter. Postgres splits words with `search_words`, which does not
  split letter/digit or acronym boundaries, so a query such as `get http status`
  names `getHTTPStatus` in SQLite but not in Postgres.
- **Postgres.** Search is one CTE query. Lexical scoring is the same BM25F as
  SQLite's, computed in SQL over the lexemes of the generated
  `search_text tsvector` (weight A qualified name, B title, C parameter names, D
  description and parameter descriptions). Each lexeme also counts as its folded
  form (`fold_plural`, migration 0002), the query words are split by the same
  `search_words` and weighted by the same rules, and typo expansion computes the
  same trigram Jaccard similarity against the catalog's vocabulary, in SQL over
  `token_trigrams` (migration 0003). The statistics come from a search index
  (migration 0004) that triggers on `tools` keep in the writing transaction:
  `search_postings` (each tool's tokens, folded forms included, with their
  per-field counts), `search_docs` (each tool's field lengths), `search_vocab`
  (each token's document frequency and trigram count), and `search_vocab_grams`
  (each vocabulary token's trigrams). A query reads the postings of its terms,
  the vocabulary rows of its words, the trigram rows of a misspelt word's
  trigrams, and one aggregate over `search_docs` for the document count and
  average lengths. Counts are stored as integers and cast to `float8` before any
  arithmetic, so the scores are exactly those of the earlier query, which
  derived everything from every tool's `search_text` per search. Writes to one
  user's catalog (`ApplySync` of a successful sync, `DeleteCatalog`) take a
  per-user advisory lock before any row lock: they share vocabulary rows, which
  concurrent writers would otherwise lock in different orders and deadlock on.
  Catalog writes are a sync per connector, so the serialisation costs little;
  other users' writes do not wait. `ts_rank` was tried first and rejected: it
  has no idf and no length normalization, and on the golden fixture it reached a
  mean top-5 overlap with SQLite of 0.65 and lost five expected results. Vector
  candidates are `embedding <=> $v` over rows with the query's model identity
  and vector length, distance below 1 (cosine above 0), ordered with `LIMIT 50`.
  Both lists are ranked with `row_number()` (ties by qualified name in the `"C"`
  collation) and fused in SQL; the connector filter, `OFFSET`, and a `LIMIT` of
  one row past the page (for `has_more`) come last. Scores are summed in a fixed
  order, so tools with identical text tie exactly and pages are stable. There is
  no HNSW index: column dimensions vary by model, and an exact scan is fine at
  this scale. The two drivers can still differ in the lower places: the tsvector
  has one field (D) for the description and the parameter descriptions, scored
  at the description's weight 1.0 with one length; and `search_words` does not
  split letter/digit or acronym boundaries. Parity is tested as top-5 overlap,
  not identical order ([§10](10-testing.md)); on the golden fixture every query
  overlaps by at least 4 of 5 except three named near-ties at 3 of 5, and
  Postgres meets every golden expectation, first places included.
- **Postgres search latency.** The budget is a p95 under 50 ms for a lexical
  search of a 5,000-tool catalog: search is one step of an agent turn whose
  model call takes hundreds of milliseconds, and 50 ms keeps it well under the
  ~100 ms at which a pause becomes noticeable. A query embedding round trip,
  when hybrid, comes on top and is cached (below). `BenchmarkSearchAt5k`
  (`make bench-postgres`) measures it: 25 copies of the golden fixture under
  distinct connector names, each description padded with pseudo-words (about
  5,000 tools and 7,000 vocabulary tokens), cycling through the golden queries
  on the `pgvector/pgvector:0.8.1-pg17` container. On an Apple M5 Pro, the
  earlier query, which unnested every tool's `search_text` per search, took p50
  285 ms and p95 371 ms; the search index (migration 0004) brings that to p50
  6–8 ms and p95 22–27 ms. The slowest queries are natural-language ones whose
  stop words (`a`, `the`, `to`) are in almost every tool, so they score almost
  every posting; their cost, and so p95, grows about linearly with the catalog
  (p95 12 ms at 2,400 tools), which puts the budget's limit near 10,000 tools.
  Past that, dropping terms with a very high document frequency (their idf is
  near 0) before scoring is the next step, at the cost of exact parity with
  SQLite.
- **Postgres edge cases.** Two differences only a hand-made definition or a
  pathological one reaches. JSON keys are case-sensitive in Postgres's generated
  columns (`->>'title'`, `->>'description'`), while `store.NewTool` uses Go's
  `encoding/json`, which matches keys case-insensitively: a definition with
  `"Description"` is indexed by SQLite but has no description in Postgres. The
  Syncer stores `mcp.Tool` re-encoded by Go, with lowercase keys, so synced
  catalogs never hit this. And a tsvector keeps at most 256 positions per lexeme
  and clamps positions above 16,383, merging duplicates, so in a very long
  definition a word's count can fall short of SQLite's; BM25 saturation (k1 =
  1.2) makes that negligible for ranking.
- **Unicode and the database locale.** Both drivers classify and lowercase
  letters by Unicode rules, so é, ü, ñ, and CJK are word characters on either.
  SQLite's tokenizer is Go (`unicode.IsLetter`, `IsDigit`, `IsUpper`). In
  Postgres, regex classes, `lower()`, and `pg_trgm` follow the database's
  `LC_CTYPE`, and a `C` ctype treats every non-ASCII letter as punctuation and
  never lowercases it. So `search_words` pins the ICU root collation
  (`COLLATE "und-x-icu"`) for its regexes and lowercasing, and typo expansion
  counts trigrams with `token_trigrams` instead of `pg_trgm` (migration 0003,
  which also recomputes stored `search_text`). The default tsvector parser
  already treats non-ASCII characters as letters under a `C` ctype, and it only
  sees lowercase alphanumeric words separated by spaces. Search therefore works
  on any `LC_CTYPE`, `C` included. The database must be `UTF8` (tool definitions
  are UTF-8 JSON) and the server must be built with ICU, as the pgvector images
  and most distributions are; otherwise `postgres.Open` refuses it with
  `ErrUnsupportedDatabase` and says which requirement failed. The shared store
  suite (`internal/store/storetest`) runs every case on a default-locale
  database and on a `UTF8` database with `LOCALE 'C'`.
- **Query embeddings** go through an LRU cache of 256 entries keyed by
  `(model identity, query)`, with the `embedding.timeout` deadline. On timeout
  or error, that query runs lexical-only, and a debug log records why. Failures
  are not cached, so the next search of the query tries again. The gateway owns
  the cache ([§7.6](7.6-gateway.md)); the store only receives the vector and its
  model identity.
