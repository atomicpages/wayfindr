# §7.2 `upstream`

Part of the [Wayfindr technical design](../design.md). Go code cites this file
as "design §7.2".

```go
type Manager struct{ /* connectors map, per-connector mutex, reaper */ }

func New(opts Options) *Manager
func (m *Manager) Apply(ctx context.Context, set config.Connectors, changes config.Changes) // carry out a Diff
func (m *Manager) ListTools(ctx context.Context, connector string) ([]*mcp.Tool, error) // follows cursors; records ToolsTTL
func (m *Manager) PeekTools(ctx context.Context, connector string) ([]*mcp.Tool, error) // ListTools without recording ToolsTTL (/admin/tools)
func (m *Manager) Call(ctx context.Context, connector, tool string, args json.RawMessage) (*mcp.CallToolResult, error)
func (m *Manager) Continue(ctx context.Context, connector, tool string, args json.RawMessage, in Input) (*mcp.CallToolResult, error) // answer what a result asked
func (m *Manager) Discard(state string) // nobody will answer: the upstream gets cancel
func (m *Manager) Retry(ctx context.Context, connector string) error // reconnect after a fix; nil = ready
func (m *Manager) SecretChanged(ctx context.Context, name string) []ConnectorStatus // retry the connectors waiting on secret name
func (m *Manager) CredentialChanged(ctx context.Context, connector string) ConnectorStatus // reconnect after a token was stored or deleted
func (m *Manager) Drop(ctx context.Context, connector string) error // close the session; state kept, next use reconnects
func (m *Manager) Hold(ctx context.Context, connector string) (release func(), err error) // uses wait until release
func (m *Manager) Status() []ConnectorStatus // sorted by connector name
func (m *Manager) Close(ctx context.Context) error // ctx bounds the url closes

type ConnectorStatus struct {
	Connector    string
	State        State
	Reason       string    // technical, for logs: never a secret, header value, or URL query; never shown to a user
	Since        time.Time // when State was entered
	NotReadySince time.Time // last ready, or added; kept across not-ready states; zero while ready (the stuck warning)
	Kind         Kind      // of the *Error that put the connector in State; empty in starting and ready
	Case         Case
	Ref          string    // e.g. "secret:linear" for missing_value
	ProviderCode string
	Link         string    // the error's auth link, else (needs_auth) Options.AuthURL's
	ToolsTTL     time.Duration // the last ListTools' cache hint (ttlMs); 0 = none (§7.8 step 3)
}
func (s ConnectorStatus) Advice() Advice // the one reading of a connector's state

// Options, set by daemon in New:
Logger         zerolog.Logger
Resolver       config.Resolver // resolves ${env:…}/${secret:…} on every transport build
Version        string          // clientInfo version sent upstream; "" = "dev"
Now            func() time.Time // state and idle times; nil = time.Now
OnToolsChanged func(connector string) // list_changed notification, every new session
OnStateChanged func(connector string, s State)
AuthTransport  func(c config.Connector, next http.RoundTripper) http.RoundTripper // c: the dialed config
ConnectTimeout time.Duration // zero means 60s
InteractionTTL time.Duration // a parked question's life; zero means InteractionTTL (10m)
AuthURL        func(connector string) string // the daemon's /auth/<connector>
```

`Acquire(ctx, connector)` exists only in `export_test.go`: tests that hold a
session across a reap use it, and production code never needs the
`*mcp.ClientSession`.

`Apply` carries out the `config.Changes` that `config.Diff` computed between the
previous config and the one whose connectors are `set` ([§7.8](7.8-daemon.md)).
It does not diff on its own: the daemon's reload owns the one current config.
The manager keeps each connector's config only to dial it. `Removed` connectors
are closed; `Added`, `Changed`, and `URLChanged` ones are rebuilt from `set`
(the connection is closed and dialed again), except that a `URLChanged`
connector that `UsesOAuth()` goes to `needs_auth` without connecting, since its
tokens are bound to the old url; `Unchanged` ones are left alone.

**`ConnectorStatus.Advice()`** is the only reading of a connector's state;
`wayfindr status`, `wayfindr secret set`, and `search_tools`' `unavailable` all
render it unchanged, so a user and an agent are told the same thing. A `ready`
connector has none. A connector an error put in its state gets `Advise` of that
error (Kind, Case, Ref, ProviderCode, Link). A state entered without one reads
as the Kind it stands for (`needs_auth` → `needs_auth`, `auth_error` →
`auth_config`, `unreachable` → `unreachable`), and `starting` has its own
wording ("The connector is still connecting." / "Try again in a moment."). It
never shows `Reason`, which stays in logs. The link comes from the error that
caused the state; the manager fills a `needs_auth` error that has none from
`Options.AuthURL`, which also supplies a `needs_auth` status's link, so the
error `Call` returns and the status carry the same one. `Kind`, `Case`, and
`Ref` also let `SecretChanged` find the connectors waiting on a secret (see
Recovery); they stay daemon-side and are not in the admin JSON.

- **SDK client per connector.** Each connector gets one `mcp.Client` that
  advertises elicitation (form and URL) and nothing else (the default would
  advertise roots), registers an elicitation handler, and sets
  `MultiRoundTrip.Disabled = true`, so `Call` sees `input_required` rather than
  the SDK answering it. The SDK negotiates the protocol version.
- **Elicitation (ADR 0008).** A call whose upstream asks the user something
  returns a result with `InputRequests` (elicitations only) and a `RequestState`
  for `Continue`, rather than an error:
  - _2026-07-28_: the upstream's `input_required`, its `requestState` prefixed
    `u:`.
  - _Earlier versions_: the upstream sends `elicitation/create` while the call
    waits. Each call is a `run` whose `tools/call` goes on in its own goroutine.
    The handler hands the question to the connector's only run in flight, and
    the waiting `Call` parks it as an **interaction**, keyed by a random id
    (state `i:<id>`). The run keeps its lease. Its connector timeout (a pausable
    clock) stops while it is parked, and the interaction TTL (10 minutes)
    applies; on expiry or `Discard` the upstream gets `cancel`. `Continue` sends
    the answer and waits for the result or the next question. With more than one
    run in flight, the question can't be tied to a call: it is declined with
    `-32010`, and the call fails `interactive_input` (`concurrent_calls`).
    Closing a session waits for its calls in flight, and the SDK sends nothing
    but notifications once a close starts, so a parked question is answered
    `cancel` first: `Close` waits for those runs to end (bounded by its ctx),
    and a session close under `c.mu` gives the upstream 5s to return, then
    cancels the run. A missing answer re-asks the question (SEP-2322).
  - _Sampling_ stays declined: a receiving middleware answers
    `sampling/createMessage` with JSON-RPC code `-32010` (in the range MCP
    leaves to implementations), and an `input_required` that asks for sampling
    is declined too, both `interactive_input` (`sampling`). The decline is
    detected per call, from that call's own error code, or from an `isError`
    result quoting the decline's message. A Go SDK server checks the client's
    capabilities first and fails the call with its own uncoded text ("client
    does not support sampling"/"elicitation"), which `Call` matches; a test pins
    the elicitation text at 2025-06-18 and 2025-11-25.
- **Transports.**
  - _stdio_: our own `stdioTransport` (`exec.Cmd` + `mcp.IOTransport`) with
    resolved `args` and `env`, and `WAYFINDR_*` stripped from the inherited
    environment. The child runs in its own process group (a job object on
    Windows), so close and reap stop launcher grandchildren too: close stdin,
    then terminate the group, then kill it, 5s apart. The child's stderr goes to
    the log at debug level, tagged with the connector name.
  - _Streamable HTTP_: `mcp.StreamableClientTransport{HTTPClient: c}`.
  - _SSE_: `mcp.SSEClientTransport{HTTPClient: c}`.

  `c`'s transport is, from the inside out: the connector's base transport
  (`Options.Clients`, its `[tls]` table; else `http.DefaultTransport`); an
  origin guard; a header injector (resolved `headers`); `Options.AuthTransport`,
  which the OAuth broker plugs into ([§7.3](7.3-auth.md)); the halt transport;
  and, for Streamable HTTP, the initialize probe. The origin guard refuses any
  request whose scheme, host, and port differ from the connector's `url` before
  anything is dialed, so a redirect to another origin (https to http included)
  and an SSE `endpoint` event naming one never carry the headers, the token, or
  the client certificate; a redirect within the origin is followed
  (wayfindr-twbw). `AuthTransport` gets the config the connector is dialed with,
  `Name` set; since a config change closes the connection and dials again, that
  config is never stale. Templates are resolved on every connect, so a changed
  secret takes effect without a reload.

- **SSE fallback.** Connect with Streamable HTTP first. If the connect fails and
  the first POST got a 4xx other than 401/403, retry with SSE. 401 and 403 are
  auth failures, which SSE would meet too. A connector that fell back stays on
  SSE, in memory, until its config changes. `transport = "sse"` skips the
  Streamable attempt.
- **Lifecycle.** `Apply` connects every added or changed connector in parallel
  (spawning stdio children) and returns once each has settled. A session that
  ends, or whose use fails below the protocol, is closed and recreated by the
  next use. A reaper running once a minute closes any stdio session idle longer
  than 10 minutes; the connector stays `ready`, and the next use spawns a new
  child.
- **Sync-on-session.** Every new session, on any transport, fires
  `OnToolsChanged`: `Apply`'s connect, a stdio spawn, a reconnect after the
  session ended or a connect failed, and `Retry`. So does an upstream's
  `list_changed`. A new session may serve different tools than the last, and
  recovery always opens one, so this one hook also re-syncs a connector when it
  recovers. The daemon wires it to `Syncer.Request` ([§7.4](7.4-catalog.md)).
- **Callbacks.** `OnToolsChanged` and `OnStateChanged` run with no manager or
  connector lock held. Events are queued per connector under its lock and
  delivered once the goroutine that caused them (`Apply`, `Retry`, `Call`,
  `ListTools`, or the session's notification handler) has released its locks;
  `Apply` delivers after releasing its own. So a callback may call `Status`,
  `Call`, `ListTools`, `Retry`, and `Apply`, on its own connector too. It must
  not call `Close`: a callback may run on a session's goroutine, which closing
  the session waits for. One connector's callbacks run one at a time, in event
  order; events a callback's own calls cause are delivered after it returns.
  Callbacks should return quickly, since `Apply` returns only once its
  connectors' callbacks have. A goroutine that finds another delivering its
  connector's callbacks leaves its own events to it and returns at once, except
  in `CredentialChanged` and `SecretChanged`: they wait until the callbacks
  their connects queued have been called (the new session's `OnToolsChanged`
  among them), so the daemon can wait for the sync that call requested
  ([§7.8](7.8-daemon.md) step 5, wayfindr-t08.9). A callback must not call
  either: it would wait on itself.
- **Close.** `Close(ctx)` stops the reaper and every upstream. `Apply` after
  `Close` does nothing and logs a warning, since no reaper would stop the
  children it spawned. Every session close takes a `ctx` (`Close`'s, `Drop`'s,
  `Apply`'s, or the use's), but the SDK's `ClientSession.Close` takes none and
  bounds a Streamable HTTP session's `DELETE` only at 5s. So each url
  connector's HTTP client has a halt transport outermost, around the broker's:
  halting it ends every request in flight, response bodies included, and fails
  any sent after. A session's close halts its own transport when its `ctx` ends,
  and the manager halts every connector's when `Close`'s `ctx` ends, which also
  frees a close waiting on a connector's lock that a stuck `DELETE`, list, or
  connect holds (wayfindr-t08.12). `Close` returns once each close has, wrapping
  `ctx.Err()` if it halted, so no request of theirs, nor the broker's token
  write on one, outlives it into the store's close. A stdio child's stop is not
  halted: it has its own bound (stdin close, then terminate, then kill, 5s
  each), and `Close` waits for it, since a child left running would outlive the
  daemon.
- **Concurrency.** One mutex per connector guards session creation only. `Call`
  runs concurrently over an established session.
- **Timeouts.** The connector's `timeout` (default 120s) is a context deadline
  over the whole `Call` or `ListTools`, connecting included. Each connect (spawn
  or dial, plus `initialize`) also has a 60s connect timeout and runs on a
  context detached from the caller's, since the SDK ties long-lived streams (the
  SSE GET) to it; the caller's context, or the connect timeout, cancels it only
  while the connect is in progress. A connect given up before the upstream
  answered (timeout or caller gone) marks the connector `unreachable`, never
  leaving it in `starting`. The connector timeout is applied with
  `context.WithTimeoutCause` and a private cause, which is how it is told apart
  from the caller's own deadline.
- **Errors.** Every failure of `Call` and `ListTools` is an
  `*Error{Connector, Kind, Case, Link, Ref, ProviderCode, Err}` (the seam-error
  convention, CODING_STANDARDS: Seam errors), narrowed with `AsError`. `Error()`
  reads `connector <c>: <kind>[ (<case>)][: <cause>]` with URLs redacted;
  user-facing wording comes only from the co-located
  `Advise(*Error) Advice{Summary, Action, Link}`, which covers every Kind and
  Case. Kinds and their Cases:
  - `unknown_connector`: no such connector, or removed mid-use.
  - `needs_auth` (state `needs_auth`; `Link` is the daemon's
    `/auth/<connector>`): `no_credential`, `url_changed`, `client_changed`,
    `authorization_server_changed`, `credential_unreadable`, `refresh_failed`,
    `token_revoked`, `provider_error`, `token_rejected`, `step_up`,
    `registration_expired`.
  - `auth_config` (state `auth_error`): `client_rejected`, `issuer_mismatch`,
    `no_registration`, `registration_rejected`, `unresolved_value`,
    `invalid_url`, `no_authorization_server`, `no_metadata`, `pkce_unsupported`,
    `auth_method_unsupported`, `signing_key_invalid`, `invalid_template` (a
    malformed `${…}`), and `secret_unreadable` (a `${secret:…}` whose stored
    value can't be decrypted, likely after a master key change; `Ref` names it,
    and `Advise` says to store it again with `wayfindr secret set <name>`).
  - `missing_value` (state `auth_error`; `Ref` is e.g. `secret:linear`):
    `secret`, `env`.
  - `interactive_input`: `sampling`, `concurrent_calls` (see Elicitation above).
  - `input_expired`: `Continue` named an interaction that expired, was
    discarded, or was answered already.
  - `timeout`, `canceled`, `rejected` (the upstream answered with a JSON-RPC
    error, such as an unknown tool): no Cases.
  - `unreachable` (state `unreachable`): `connect_refused`, `connect_timeout`,
    `connect_canceled`, `spawn_failed`, `auth_server`, `provider_unavailable`,
    `auth_internal`.

  Auth errors are matched by behaviour (`NeedsAuth()`, `AuthConfig()`,
  `AuthCase()`, found through net/http's `*url.Error`), and each of auth's
  `AuthCase()` values is translated into the Case above of the same name, except
  auth's `transport`, `malformed_response`, and `unexpected_status` (→
  `auth_server`) and `store` and `not_replayable` (→ `auth_internal`). An
  unknown value gives no Case.

  A resolver failure arrives as a `*config.ResolveError`, which names the
  reference, whoever resolved it: the Manager for the connector's url, headers,
  and env, or auth for its own config (a `client_secret`, say), whose
  `auth_config` error wraps it. `resolve` reports the reason through config's
  sentinels, so `upstream` matches only those: wrapping `config.ErrNotFound` it
  is `missing_value`; wrapping `config.ErrUnreadable` (the sealed secret exists
  but won't open) it is `auth_config`/`secret_unreadable`. Either way `Ref`
  names the reference, so setting the secret reconnects the connector
  (`SecretChanged`). Any other resolver failure (store I/O) is `unreachable`,
  and retried; carried by auth, it stays auth's `auth_config`.

  **One verdict.** Every connect and every use ends in one pure
  `judge(outcome) verdict`. The outcome is the phase (connect or use), the
  error, whether this call's input request was declined, and how the context
  ended; the verdict is the state event (or none), the redacted reason, whether
  to close the session, and the `*Error`. The first rule that matches decides:
  1. success → synced;
  2. `needs_auth`;
  3. a `${…}` that won't resolve, whoever carries it: `auth_config`
     (`invalid_template`, `secret_unreadable`) or `missing_value`, naming the
     reference; before auth's own `auth_config`, which would hide it;
  4. `auth_config`;
  5. `interactive_input` → synced (the upstream answered);
  6. `timeout`, or else `canceled`, in the use phase only → state untouched;
  7. `rejected`, in the use phase only → synced;
  8. `unreachable` → transport error. A connect given up on (connector timeout,
     connect timeout, or caller gone) lands here, so it never leaves the
     connector in `starting`, and so does a JSON-RPC error during `initialize`.

  Rules 2–4 and 8 close the session, since the failure is below the protocol;
  5–7 leave it open. The Manager only applies the verdict: under the connector's
  lock it checks for removal (→ `unknown_connector`, state untouched), closes
  the session if it is still the one the use ran over, and applies the event. A
  failed connect is always recorded, even when the caller gave up. The gateway
  renders the errors through `Advise` ([§7.6](7.6-gateway.md)).

- **Recovery.** Each connector keeps an _epoch_, which goes up each time it
  enters `needs_auth` or `auth_error` (from itself included), and each session
  records the epoch it was opened in. A success (a synced verdict) over a
  session opened in the current epoch, so after the connector entered that
  state, means the user fixed the problem and the upstream accepted it: the
  Manager applies `authorized` and then `synced`, so the connector goes through
  `starting` to `ready`. A success over an older session (one still finishing a
  call it sent before the revoke) is stale, and the state machine refuses it.
  The comparison is made where the verdict is applied, from the session's lease;
  `judge` stays pure. Since `needs_auth` and `auth_error` close the session, the
  next use connects a new one, so the first call after the user authorizes
  recovers the connector on its own. `Retry(ctx, connector)` does it at once:
  from `needs_auth`, `auth_error`, or `unreachable` it drops the session, fires
  `authorized` (→ `starting`), connects, waits for the connect to settle (at
  most the connect timeout), and returns the connect's `*Error`, or nil once
  `ready`. It returns nil for a `ready` connector without touching it, waits out
  a connect in progress in `starting`, and returns `unknown_connector` for a
  name it doesn't know. The session it opens fires `OnToolsChanged`, as every
  new session does, so the catalog re-syncs on recovery. The manager, which owns
  `Kind` and `Case`, also decides who a change affects, so callers name the
  change, not the connectors:
  - `SecretChanged(ctx, name)` retries, in parallel, every connector whose last
    error is `missing_value` or `secret_unreadable` on `Ref` `secret:<name>`,
    and returns their statuses, sorted, once each connect has settled (none when
    nothing waited). `${env:…}` references are not covered: the daemon's
    environment is fixed. `PUT /admin/secrets/{name}` calls it through the
    daemon's recovery module ([§7.7](7.7-httpd.md), [§7.8](7.8-daemon.md) step
    5).
  - `CredentialChanged(ctx, connector)` follows a change of the connector's
    OAuth credential, in either direction, by one rule: in any state it drops
    the session and connects at once (through `starting` from `needs_auth`,
    `auth_error`, or `unreachable`, as `Retry`), so the broker's transport reads
    the credential as it now is. A new token makes the connector `ready`; a
    deleted credential puts it in `needs_auth` (`no_credential`) now, not on its
    next use. Nothing in `upstream` is revoke-specific. It returns the settled
    status; a connector the manager doesn't know (a credential whose connector
    left the config) gets a status with no `State` and `Kind`
    `unknown_connector`. The daemon's recovery module calls it from the broker's
    `OnCredentialChanged` ([§7.3](7.3-auth.md), [§7.8](7.8-daemon.md) step 5).
  - `Drop(ctx, connector)` closes the connector's session and leaves its state
    alone; the next use connects again. The daemon's revoke calls it before the
    broker deletes the credential, so the session's close (a Streamable HTTP
    `DELETE`, through the broker's transport) still carries the token and a
    stateful upstream ends the session (wayfindr-zgp.13). A connector it doesn't
    know has nothing to drop. `ctx` bounds the `DELETE` too, as it bounds every
    session close (see **Close**).
  - `Hold(ctx, connector)` keeps every new use of the connector (a call, a list,
    a retry or reconnect, `Apply`'s connect) from starting until the returned
    `release`: `acquire` waits for it under the per-connector mutex, and a use
    whose `ctx` ends while waiting fails `canceled` (or `timeout`) without a
    state change. Uses already under way carry on. One hold at a time. The
    daemon's revoke holds the connector from before `Drop` until the credential
    is deleted, so no use racing the revoke opens a session with the token in
    between that would later be closed without it (wayfindr-t08.10).
- **Redaction.** Error text, state reasons, close and protocol errors, and each
  stdio stderr line pass through `internal/redact`, which masks the userinfo,
  query, and fragment of every URL ([§9](9-security.md)).

**State machine** (states from [GLOSSARY.md](../../../GLOSSARY.md)):

```
          Apply(add/changed)
                │
                ▼
           ┌─────────┐ sync ok  ┌───────┐
           │starting ├─────────►│ ready │◄──────────────┐
           └──┬───┬──┘          └─┬───┬─┘               │
   auth needed│   │transport err  │   │ transport err   │ sync/call ok
              │   ▼               │   ▼                 │
              │ ┌───────────┐     │ ┌───────────┐       │
              │ │unreachable│◄────┼─┤unreachable├───────┘
              │ └───────────┘     │ └───────────┘
              ▼                   │ refresh failed / 403 step-up / url changed
        ┌──────────┐◄─────────────┘
        │needs_auth├──── authorized (Retry, or a success on a new session) → starting
        └──────────┘
        ┌──────────┐
        │auth_error│◄── config can't work (no PKCE, no client_id/DCR, issuer, missing ${…})
        └──────────┘──── config changed, or authorized (Retry, or a success on a new session) → starting
```

`unreachable` also leaves on `authorized` (Retry) → `starting`. In `needs_auth`
and `auth_error`, a success over a session opened before the connector entered
the state is stale and ignored (see Recovery above).

Idle shutdown of a stdio process doesn't change the connector's state; it stays
`ready`. Removing a connector deletes it from the manager entirely.
