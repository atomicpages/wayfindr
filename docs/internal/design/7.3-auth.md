# §7.3 `auth`

Part of the [Wayfindr technical design](../design.md). Go code cites this file
as "design §7.3".

```go
type Broker struct{ /* credentials module, Discoverer, Registrar, http client, flow table, singleflight.Group */ }

func (b *Broker) Transport(c config.Connector, base http.RoundTripper) http.RoundTripper
func (b *Broker) Link(connector string) string                                // http://<listen>/auth/<connector>, escaped
func (b *Broker) Revoke(ctx context.Context, connector string) (bool, error) // cancel flows, delete the row; false: none
func (b *Broker) Close()                                                     // daemon, at shutdown: end pending flows, wait for the device code pollers
func (b *Broker) Health(ctx context.Context, c config.Connector) (Health, error) // expiries a status and warnings read; zero: none, unknown, or old url
func Probe(ctx context.Context, client *http.Client, resource string) (ProbeResult, error) // connector add: OAuth, open, or unknown

type Flows struct{ /* broker, lookup */ }                                     // the one flow entry, for both doors
func NewFlows(b *Broker, lookup func(string) (config.Connector, bool)) *Flows
func (f *Flows) Start(ctx context.Context, name string, opts StartOptions) (Flow, error) // lookup + OAuth check + start; Flow{ID, Connector, Prompt, ExpiresAt}
type StartOptions struct{ Device bool }                                       // the device code whatever the grant; zero: the grant decides
type Prompt struct{ AuthorizeURL, UserCode, VerificationURI, VerificationURIComplete string } // authorization code: AuthorizeURL; device code: the rest
func (f *Flows) Wait(ctx context.Context, id string) (FlowResult, bool)       // until done/failed/expired/ctx; false: unknown id
func (f *Flows) HandleCallback(w http.ResponseWriter, r *http.Request)        // GET CallbackPath
func (f *Flows) ConfigChanged()                                               // daemon, on every reload: cancel outdated flows
func NewPages(f *Flows) *Pages                                                // Confirm (GET /auth/{c}), Start (POST)
func HTTPStatus(err error) int                                                // a flow that cannot start, for both doors
const CallbackPath = "/oauth/callback"

OnCredentialChanged func(connector string) // BrokerOptions; daemon recovery → Manager.CredentialChanged → Syncer.Await
```

## Module layout

`auth` models upstream OAuth as three independent axes (ADR 0018): the grant,
client authentication, and the sender constraint. It stays one package, one
concept per file, with dependencies in one direction: grants and the transport
use the concepts, and the concepts use the kernel.

- **Kernel** (value types, no policy). `token.go`: the token. `oauthclient.go`:
  `oauthClient`, everything needed to talk to one connector's authorization
  server (connector, issuer, endpoints, the `Registration`, its `clientAuth` and
  `sender`, the HTTP client, the Inspectors, the clock), built only by
  `Broker.oauthClient`, which also holds `endpointsFor`, the one rule for when
  the mTLS endpoint aliases replace the token, device authorization, and
  registration endpoints. `endpoint.go`: `oauthClient.exchange`, the one token
  endpoint call: it applies the client authentication and the sender, sends,
  reads the bounded body, runs the Inspectors, and gives every failure its Case.
- **Concepts.** `clientauth.go`: `clientAuth`, one small type per method
  (`noClientAuth`, `secretBasic`, `secretPost`, `secretJWT`, `privateKeyJWT`,
  `tlsClient` for both tls methods, and `unusableClientAuth` for a client that
  cannot authenticate), and its one selector `chooseClientAuth`. `jws.go`: the
  sign-only JWS the JWT methods use, and the signing key's parsing. Nothing else
  knows how a method works. `sender.go`: `sender`, which adds to token requests
  and upstream requests, sees every answer (`observe`), and may ask for one
  retry; `bearer`; `unusableSender` for a sender constraint that cannot be met;
  and its one selector `chooseSender(cfg, disc, challenge)`. `dpop.go`: the DPoP
  sender (RFC 9449; see "DPoP" below), its key, its proofs, and the nonce cache.
- **Grants.** `flows.go`: the flow table and `Flows`, generic over a `flowKind`
  (its grant type, its `check` before a client is chosen, its `begin`, which
  returns the `Prompt`, and `armed`), chosen only by `selectFlowKind`, and
  `completeFlow`, the shared completion (the config check and `storeGrant`).
  `flow_authcode.go`: the authorization code (PKCE, which is its `check`,
  `state`, the authorize URL, the callback, the code exchange).
  `flow_device.go`: the device code (RFC 8628; see below). `refresh.go`:
  renewing a stored grant's token (`refreshOnce`, `redeem`). The unattended
  grants (see below) are each one function,
  `unattendedGrant(ctx, oauthClient, scopes) (url.Values, error)`, that builds
  the grant's form: `grant_clientcredentials.go` (`client_credentials` and
  `scope`) and `grant_jwtbearer.go` (the jwt-bearer `grant_type`, `assertion`,
  and `scope`, with the assertion from its source).
- **Transport.** `transport.go`: the `roundTripper`, which takes tokens from a
  `tokenSource` and sends them through a `sender`. That sender is not chosen per
  connector: `Broker.Transport` gives every Transport the `dpop` sender with no
  key, which sends each token as it was bound, with a proof of the DPoP key the
  token carries, or as a bearer token when it carries none (ADR 0018, amended).
  On a 401 it lets the sender retry first, then renews the token once, and on a
  403 `insufficient_scope` it steps up: the token source either fails the
  request or hands back a token to replay it with once. A second refusal (401 to
  the renewed token, 403 to the stepped-up one) goes to the token source's
  `refused`, which words it, so the policy lives in the source.
  `storedtokens.go`: `storedTokens`, the `tokenSource` of an auth flow's
  connector (the credentials row, lazy refresh; its step-up records the scopes
  and fails `step_up`; a refused refreshed token is `token_rejected`).
  `unattended.go`: `unattendedTokens`, the `tokenSource` of an unattended grant
  (see below).
- `broker.go` keeps the Broker's wiring, options, `Link`, `fail`,
  `storeGrant`/`credentialChanged`, and the choice of the Transport.

Rules that keep each path self-contained:

- Grants never call each other.
- Concepts never know about grants.
- The transport knows only `tokenSource` and `sender`.
- Only `storedTokens` (with its refresh), the flows, the Registrar, and revoke
  touch the credentials module (`Health` reads it, and skips an unattended
  connector). `Broker.load` and `Broker.storeGrant` in `broker.go` are the doors
  the first two share. `unattendedTokens` never does, so an unattended connector
  has no stored credential by construction.
- Each concept has exactly one selector (`chooseClientAuth` for client
  authentication, `chooseSender`, which only `Broker.oauthClient` calls through
  `senderFor`, for the sender of a grant's token requests, `Broker.Transport`
  for the token source, `selectFlowKind` for the auth flow kind). Every policy
  decision lives there, not in callers. The configured
  `token_endpoint_auth_method` reaches `chooseClientAuth` only through the
  `Registration` the Registrar builds; for `jwt_bearer`, the Registrar puts the
  signing key in `AssertionKey` and leaves `SigningKey` nil unless the method is
  `private_key_jwt`.

## Behaviour

- **`OnCredentialChanged`** is called after a connector's credential changed,
  other than by a refresh (which renews the same grant): a token from a new
  grant was stored, or the credential was deleted. Every token from a new grant
  is stored through the broker's `storeGrant`, which calls it; the flow's
  completion (`HandleCallback`, wayfindr-421) stores the exchanged code's token
  there, and `Revoke` (wayfindr-141) calls it once the credential row is
  deleted. It runs on the goroutine that changed the credential (the browser's
  callback request, for the flow), so the daemon's recovery module runs
  `Manager.CredentialChanged` in the background ([§7.8](7.8-daemon.md) step 5).
- **One owner of the credentials row** (wayfindr-zgp.22). An unexported module
  in `auth` (`credentials`: store, sealer, user ID, one mutex) is the only code
  that reads or writes a credentials row, seals or opens its token or DCR
  client, or knows their AAD. The broker owns it and hands it to its Registrar
  through the Registrar's constructor. Reads return an opened view (`grantView`:
  token, DCR client, issuer, redirect URI, requested scopes, and an unexported
  version, the sealed token, for compare-and-swap). A token read takes the
  connector's configured resource, and a token bound to another one is
  `url_changed`: that check lives only in the module. Writes are named, each
  with its rule: `grant`, `register`, `renew`, `addScopes`, `forgetClient`, and
  `delete`.
- **Row lock.** Every write is a read-modify-write under the module's lock: a
  grant, a DCR client, a refresh's token, a step-up's `requested_scopes`, a
  forgotten DCR client, and a revoke's delete, so writers of different fields
  never overwrite each other (wayfindr-zgp.10). Cancelling flows takes it too.
  It is a plain mutex, one daemon (ADR 0003); server mode would replace it,
  there only, with a DB lock (ADR 0004).
- **Who starts a row.** Only two writes may create a credentials row: a new
  grant (`grant`, through the broker's `storeGrant`), and the DCR registration
  of the client an auth flow will be granted to (`register`; its token's refresh
  needs the client from the row). Every other write (`renew`, `addScopes`,
  `forgetClient`) amends an existing row; with none, it writes nothing and fails
  `no_credential`, so a write that raced a revoke cannot bring the credential
  back (wayfindr-zgp.16). A registration that a revoke overtook starts a row
  with the new client and no token: the revoke cancels the registering flow, but
  the registration is shared by the connector's flows and its client is not the
  revoked one, so it is kept for the next flow.
- **Compare-and-swap.** A refresh (`renew`) stores its token only if the row
  still holds the token it refreshed (compared sealed, so any token written
  since counts). Otherwise its token is dropped: after a revoke the call fails
  `no_credential`; after a new grant the call uses the grant's token, which is
  newer than anything the refresh got. A rejected DCR client is forgotten
  (`forgetClient`) on the same condition: if a token was stored since the
  refresh read the row, or since the auth flow started, the server accepted the
  client for it, so the client is kept; the refresh then uses the newer token,
  and the flow fails `registration_expired` as before.
- **`Revoke`** cancels the connector's pending flows and deletes its whole
  credentials row, both under the row lock, then calls `OnCredentialChanged`, so
  a configured connector settles in `needs_auth` (`no_credential`) through the
  one recovery path. The DCR client goes with the token: the user asked Wayfindr
  to forget the connector's authorization, a row left with only a client would
  still be listed as orphaned, and the next flow registers a new client. Nothing
  is sent to the authorization server (no RFC 7009 revocation in v1). It reports
  false, and fires nothing, when there was no row, but still cancels the pending
  flows: a flow started before the revoke must not store a credential after it.
  The connector need not be configured, so an orphaned credential is revoked the
  same way.
- **Cancelled flows.** `Revoke`, and a config change that outdates a flow, end
  the connector's pending flows as failed (`flow_cancelled`), those still
  starting too (a flow is in the flow table from the start of `Flows.Start`, so
  a revoke or reload during its discovery or registration ends it, and `Start`
  fails `flow_cancelled`). One rule in `auth` (`outdated`, wayfindr-zgp.15) says
  which config changes outdate a flow: the connector was removed, or its `url`,
  its `[auth]` table, or its `[tls]` table (`config.TLSEqual`) changed (the
  token would be bound to the old url, granted under the old client, scopes,
  endpoints, or redirect URI, or bound to the old client certificate). Any other
  change, such as `timeout`, `headers`, or `env`, leaves it pending. The rule is
  applied at the callback, which is authoritative: before the code is exchanged,
  and again under the row lock as the token is stored. It is also applied on
  every reload: the daemon calls `Flows.ConfigChanged()` once the new config is
  the running one, which sweeps the pending flows under the row lock (the daemon
  no longer picks connectors). A flow whose callback already passed that check
  under the lock is storing a token granted under the config it was checked
  against, and the sweep leaves it alone; a revoke still ends it, and deletes
  the token. So a token is either stored before the cancellation (and a revoke
  deletes it) or never. A late callback's page shows the cancellation's advice.
- **`Health`** takes the connector's current config and returns only what the
  stored credential predicts: the access token's expiry, whether there is a
  refresh token and when it ends, and when the DCR client a refresh would use
  expires. It is zero when there is no token, the token can't be opened, or it
  is bound to a url other than the configured one, so it will never be sent
  (wayfindr-zgp.14). `Health.Warnings(now, connector, link)` turns it into the
  warnings (`no_refresh`, `refresh_expiring`, `registration_expiring`) the
  daemon's health check logs and the status and `search_tools` show
  ([§7.8](7.8-daemon.md) step 8). No token leaves the broker.
- **Client binding** (wayfindr-3e6f). A grant records the client it was obtained
  with (`Credential.ClientID`, [§5](5-data-model.md)). The credentials module's
  `load` refuses a token whose recorded client differs from the connector's
  configured `client_id`, as `client_changed` (needs auth), so a token is never
  sent after the user switches apps. Only a manual connector is checked: its
  client comes from config, so a change is the user's. A discovered connector's
  DCR client is Wayfindr's own and changes on re-registration while its grant
  stays good until a refresh, which fails on its own if the client is wrong. A
  row with no client recorded (from before the column) is accepted, and a
  changed `client_secret` alone never counts.
- **Token endpoint binding** (wayfindr-afb1). Discovery follows what the MCP
  server names, so an upstream could point a refresh at another authorization
  server and collect the refresh token and the client's credential. A grant
  therefore records, in its sealed token (`token_endpoint`), the token endpoint
  it was obtained at: `Discovery.Endpoints.Token`, as discovered or configured,
  before an mTLS alias. `refreshOnce` compares it with the refresh's own
  discovery before choosing a client or sending anything; a difference (an empty
  recorded one included) is `authorization_server_changed` (needs auth), whose
  advice says to sign in again only if the new server is trusted, or to pin
  `authorization_server`. An unattended grant stores no token, so it can't be
  bound this way: its config must name the server (`authorization_server` or
  `token_endpoint`, config validation), and discovery then never takes the
  issuer from the upstream.
- **Where the PRM was** (wayfindr-q8y9). A grant also records, as `prm_url`,
  where its flow found the Protected Resource Metadata (`Discovery.PRMURL`). A
  refresh made before the token expires has no challenge, and MCP lets a server
  name its PRM only in the 401's `resource_metadata`, at a path none of the
  well-known candidates reach; without the record, discovery fell back to the
  legacy endpoints and the binding check above refused the refresh. So
  `refreshOnce` passes it as `DiscoverRequest.PRMURL`, which discovery tries
  first when the challenge names none, from the cached document. `prm_known`
  says `prm_url` holds what discovery found, empty when there was no PRM
  (`authorization_server` set, or a legacy server): every flow sets it, so
  those grants never probe. A token sealed before the fields has neither; its
  refresh discovers with `Probe` instead, and records what that discovery
  found, so it probes once.
- **`authorize_params`** are extra authorization-request parameters a provider
  needs (Google's `access_type=offline`, say). `authorizeURL`
  (`internal/auth/flow_authcode.go`) starts from the endpoint's own query, adds
  `authorize_params`, skipping every key `config.ReservedAuthorizeParam` names,
  and only then sets `response_type`, `client_id`, `redirect_uri`, `state`,
  `scope`, PKCE's, and `resource`, so a protocol parameter is always Wayfindr's,
  even one this request leaves out (no scope, no PKCE, no resource).

- **Config.** The broker keeps no copy of the connector config and has no lookup
  into one. `Transport` is the manager's `AuthTransport` and gets the config the
  connector is dialed with ([§7.2](7.2-upstream.md)); a config change redials,
  so a new or edited OAuth connector's first connect is already authorized, with
  nothing to update in the broker first. `Transport` returns `base` itself for a
  connector that doesn't `UsesOAuth()` (no auth table, or an API key in
  `headers`).
- **Discovery** is ADR 0007 step for step, with config overrides taken first.
  `oauthex.ParseWWWAuthenticate` and `oauthex.GetProtectedResourceMetadata` are
  reused. Authorization-server metadata is fetched by our own code, so that the
  `validate_issuer` opt-out can be applied. Documents are cached in
  `oauth_metadata`. A cached document is used until an auth failure, then
  fetched again once. `DiscoverRequest.Mask` (`Broker.urlMask`: each value the
  connector url's references resolved to, replaced by the reference) masks
  discovery's logs and errors, and a document whose URL or text holds one of
  those values is never cached: the cache is plaintext, and a per-user url can
  carry its key in the path. Such a connector's protected resource metadata is
  fetched each time (wayfindr-wt2v). The probe for the challenge (below) belongs
  to discovery too: the Discoverer keeps the challenge of the last probe of each
  resource URL in memory (nil for an answer without one; a probe that could not
  reach the server is not kept) and reuses it until a discovery with refetch,
  which drops it and probes again (wayfindr-zgp.20). After a restart the first
  discovery probes again.
- **Registration order** is: config `client_id`, then CIMD (only with
  `client_metadata_url` and the AS advertising support), then the stored DCR
  client if its issuer and `redirect_uri` still match, then a new DCR
  registration via `oauthex.RegisterClient`, then `auth_error`. The Registrar
  alone holds the order, for both its uses: `existing`, the client a stored
  token was issued to, for a refresh (the configured client, else the stored DCR
  client whatever it was registered for; it never registers, since a new client
  could not spend the old refresh token); and `obtain`, the client an auth flow
  authorizes as (may run DCR, single-flight per connector).
- **Device code flow** (`flow_device.go`, wayfindr-b6v9). `Flows.Start` picks it
  when `StartOptions.Device` is set or the connector's `grant` is `device_code`
  (`selectFlowKind`). Its `check` needs a device authorization endpoint:
  `device_authorization_endpoint` from config, else the metadata's (parsed from
  the cached metadata document into `MetadataExtensions`, the one parse of
  fields go-sdk's `AuthServerMeta` lacks), else `device_unsupported` (config);
  the Transport applies the same check to a `device_code` connector, as it does
  PKCE to an authorization code one. PKCE does not apply. `begin` posts `scope`
  (the authorization code's rule), `resource` (unless disabled), and the
  `authorize_params` to the endpoint through `oauthClient.post`, so client
  authentication applies but no sender proof, and returns the user code and
  verification URIs; a verification URI that is neither https nor loopback http
  is `malformed_response`, so a hostile document cannot show the user a phishing
  page. The flow expires at the device code's `expires_in`, at most `FlowTTL`.
  `armed` starts one poller per flow, whose context is cancelled when the flow
  ends (a revoke, the `outdated` sweep, `Broker.Close`), so a pending request is
  abandoned. Every `interval` (default 5s; the broker's `sleep`, a test seam) it
  sends the `device_code` grant through `oauthClient.exchange`, so client
  authentication, the sender, and the Inspectors apply, and acts on the
  Inspectors' Case: `authorization_pending` polls again, `slow_down` adds 5s to
  every later interval, `access_denied` is `authorization_denied`,
  `expired_token` is `flow_expired`, any other OAuth error ends the flow (a
  rejected DCR client is forgotten as for the callback). A poll that gets no
  answer about the grant (a transport failure, a known transient code, or a 5xx
  with no error code) doubles the interval, up to a minute, and keeps polling
  until the deadline (RFC 8628 §3.5). A token goes through `completeFlow`, whose
  check under the row lock refuses one that arrives after a revoke or a config
  change. DCR registers the device grant type too when the metadata lists it or
  the flow is a device flow, and a stored DCR client is reused only if its
  `grant_types` cover the flow's grant (RFC 7591's default is the authorization
  code alone); a device flow ignores the stored client's redirect URI, which it
  never sends. The admin API's `AuthFlow` carries `user_code`,
  `verification_uri`, and `verification_uri_complete`; the
  `POST /auth/{connector}` page and the console's sign-in render the code and a
  link instead of redirecting.
- **The client's credentials** travel in the `Registration` the Registrar
  returns, which is the only way the connector's config reaches
  `Broker.oauthClient` (the broker keeps no config): the resolved
  `client_secret`; the `signing_key`, resolved (`unresolved_value`) and parsed
  into a `crypto.Signer` with its `kid`, `alg`, and `audience` (PKCS#8, SEC 1,
  or PKCS#1 PEM; EC P-256/P-384, RSA of 2048 bits or more, Ed25519; anything
  else, or an `alg` the key cannot sign, is `signing_key_invalid`); and
  `AuthMethod`, the method fixed for the client: the configured
  `token_endpoint_auth_method`, which wins, else the
  `token_endpoint_auth_method` of the DCR registration response, which
  `openClient` reads back from the sealed client (wayfindr-9fep: it used not to,
  so a client registered for `client_secret_post` sent basic, was rejected, and
  was registered again on every flow).
- **The DCR request** asks for the configured `token_endpoint_auth_method`, the
  one the client's token requests will use; with none configured, `none` when
  the AS lists it, else `client_secret_basic` when it lists that or nothing,
  else `client_secret_post`, and names `application_type`: `native` for a
  loopback redirect URI, `web` otherwise (SEP-837; the go-sdk's
  `ClientRegistrationMetadata` has the field). A response without the method is
  taken to have registered the one asked for, and that is sealed with the
  client.
- **Client authentication** is chosen by `chooseClientAuth(reg, disc)`, the one
  selector: the fixed method; else, by the credential held, the first the AS
  lists in `token_endpoint_auth_methods_supported` (metadata without the field
  lists `client_secret_basic`, RFC 8414; with no metadata the first is taken): a
  signing key gives `private_key_jwt`, a secret `client_secret_basic`, then
  `client_secret_post`, then `client_secret_jwt`. A public client sends its
  `client_id` whatever the list says. The `tls_*` methods are never chosen: only
  a fixed method is one, and `tlsClient` sends just `client_id`, the
  connection's client certificate being the credential (RFC 8705 §2). No fit, or
  a fixed method whose credential the client lacks, is
  `auth_method_unsupported`: `obtain` returns it before the user is sent to
  authorize, and `Broker.oauthClient` turns it into an `unusableClientAuth` that
  fails every token request before it is sent. The JWT methods send
  `client_assertion_type` (jwt-bearer), `client_assertion`, and `client_id`; the
  assertion (RFC 7523 as updated by RFC 10070) has `iss` = `sub` = the client
  ID, `aud` the AS's metadata issuer (or the token endpoint for
  `audience = "token_endpoint"`, or with no issuer), a 16-byte random `jti`,
  `iat` now and `exp` 60 seconds on, and the header `typ`
  `client-authentication+jwt` with `kid` when set. `client_secret_jwt` signs
  HS256 over the secret; `private_key_jwt` signs with the configured `alg`, else
  the first of the AS's `token_endpoint_auth_signing_alg_values_supported` the
  key can sign, else the key's own (ES256, ES384, RS256, EdDSA).
- **The connector's HTTP client** (wayfindr-eqr7). Every request auth sends for
  a connector, discovery's fetches and probes, DCR, the device authorization
  request, and every token request, goes through the connector's own client,
  `BrokerOptions.Clients.For(conn)` ([§4](4-configuration.md),
  `internal/httpclient`), the one upstream uses as its base transport, so the
  authorization server and the MCP server see the same client certificate and
  are trusted by the same CAs. The Discoverer and the Registrar take it per
  request (`DiscoverRequest.Client`, `RegisterRequest.Client`); the metadata
  cache stays keyed by URL. `Broker.httpFor` builds it once per flow or refresh:
  a tls key that can't be resolved is `unresolved_value` (the
  `*config.ResolveError` kept, so upstream reads `missing_value`), a ca_file
  that can't be used `tls_untrusted`, a client certificate that can't be loaded
  `tls_handshake`. Without `Clients` (tests) the broker uses
  `BrokerOptions.Client`.
- **TLS failures.** A failure to reach the authorization server (or the
  resource, while discovering) is classified once, by `transportCase`: a
  certificate that fails verification (`*tls.CertificateVerificationError`,
  `x509.UnknownAuthorityError`, …) is `tls_untrusted`; a TLS alert the server
  sent (a `tls.AlertError`, or crypto/tls's `*net.OpError` with Op
  `remote error`, such as `certificate_required`) or a peer that doesn't speak
  TLS is `tls_handshake`; anything else `transport`. Both TLS Cases are config:
  the fix is the `[tls]` table. Upstream's own TLS failures to the MCP server
  stay unreachable ([§7.2](7.2-upstream.md)).
- **mTLS endpoint aliases** (RFC 8705 §5). `MetadataExtensions` parses
  `mtls_endpoint_aliases` and `tls_client_certificate_bound_access_tokens` from
  the metadata document. `endpointsFor`, which `Broker.oauthClient` calls (and
  the flow, for the endpoint DCR registers at), is the one rule: the aliases
  replace the token, device authorization, and registration endpoints when the
  client authentication method is a tls one, or when the connector has a client
  certificate and the authorization server binds tokens to it. A device
  authorization endpoint from config stays.
- **Certificate-bound tokens** (RFC 8705 §3) need nothing of their own: the
  token request and the MCP connection go through the same client and present
  the same certificate. The PRM's `tls_client_certificate_bound_access_tokens`
  means the resource supports them, not that it requires them, so nothing is
  checked before a call; when the resource rejects a fresh token
  (`token_rejected`) and the PRM advertises them while the connector has no
  client certificate, the error's detail says to add one in `[tls]`
  (`storedTokens.refused`, through `Broker.certBoundHint`; an unattended grant's
  401 is `grant_rejected` and carries no hint).
- **DPoP** (RFC 9449, `dpop.go`, wayfindr-5vps). The sender is chosen per grant
  by `chooseSender(cfg, disc, challenge)`, the one selector, which only
  `Broker.oauthClient` calls (with `Discovery.Challenge`, the challenge
  discovery read): `dpop = "never"` is bearer; `"always"` is DPoP unless the
  metadata lists `dpop_signing_alg_values_supported` without ES256
  (`dpop_alg_unsupported`, config, found before any request: a flow checks
  `oauthClient.usable` as it starts); `"auto"` (and unset) is DPoP when the PRM
  sets `dpop_bound_access_tokens_required`, the resource's challenge offers the
  `DPoP` scheme, or the grant already has a DPoP key (a refresh, or an
  unattended re-grant, which has no fresh challenge to read: RFC 9449 §5 refuses
  a bound refresh token without a proof), and the metadata lists ES256. The
  metadata field is parsed into `MetadataExtensions`.
  - **The key.** One ECDSA P-256 key per grant (`dpopKey`), made by
    `Broker.oauthClient` when DPoP is chosen and the caller has none. An auth
    flow makes it as it starts and keeps it on the flow; the authorize request
    names its RFC 7638 thumbprint as `dpop_jkt` (after `authorize_params`, which
    may not set it); `exchange` puts it on the token, and the token blob seals
    it as `dpop_key` (PKCS#8, base64), so the compare-and-swap covers it and
    revoke deletes it. `redeem` copies it forward as it copies the refresh
    token, and a refresh proves with it; a refresh of a token with a key
    discovers with `Probe` (the cached probe challenge), so it chooses its
    sender as its flow did. An unattended grant's key lives in its `heldToken`
    and is reused by every later grant. A token row sealed before DPoP has no
    key and is bearer.
  - **Proofs.** `typ` `dpop+jwt`, ES256, the public `jwk`; `jti` (16 random
    bytes), `htm`, `htu` (no query or fragment), `iat` on the broker's clock,
    `nonce` when one is known, and on upstream requests `ath`. Every token
    request (code exchange, refresh, client credentials, jwt-bearer, each device
    poll) and every upstream request gets a fresh proof, replays included. The
    device authorization request goes through `oauthClient.post`, which adds no
    proof.
  - **At the resource** the Transport's sender is a DPoP sender with no key of
    its own: it sends a token with its own key, with the `DPoP` scheme, when its
    `token_type` is `DPoP` (case-insensitive), and as Bearer otherwise, so an
    authorization server that declines binding still works and a token from
    before a `dpop` edit is sent as it was bound.
  - **Nonces.** One `nonceCache` on the broker, keyed by (origin, role: `as` or
    `rs`), since one origin can be both (an MCP server that is its own
    authorization server); every answer's `DPoP-Nonce` updates it
    (`sender.observe`). A 400 `use_dpop_nonce` from the token endpoint is
    retried once with a fresh proof, before the Inspectors read the answer; a
    401 with a `DPoP` `use_dpop_nonce` challenge is replayed once, before the
    token source renews.
  - **Challenges.** Discovery's `resource_metadata` and `scope`, the probe
    (`connector add`), and step-up's `insufficient_scope` read `DPoP` challenges
    as they read `Bearer` ones.
  - **Errors.** `invalid_dpop_proof` from the token endpoint is `dpop_rejected`
    (config): the proof is the same on a retry and on a new flow's code
    exchange, so only the host's clock or `dpop = "never"` fixes it. A
    `use_dpop_nonce` left after the one retry is `provider_unavailable`: a nonce
    rotated meanwhile, and the next call proves with the newer one.
- **Unattended grants** (`client_credentials`, `jwt_bearer`; ADR 0018).
  `Broker.Transport` picks `unattendedTokens` when
  `conn.Auth.Grant.Unattended()`, else `storedTokens`; nothing else in the
  transport knows the grant. `unattendedTokens` holds each connector's token in
  memory only, in the broker's `unattendedTable` keyed `userID|connector`
  (token, the scopes the grant asked for, and the `[auth]` table and resolved
  url it ran under, so a token got under another config is never used). `token`
  returns the held token, or runs the grant when there is none or it is within
  the refresh window; `renew` (after a 401) runs it again with discovery
  refetched. Grants share the broker's singleflight and key, detached from the
  caller's context with the refresh's timeout, so concurrent callers share one
  grant. A grant runs discovery as a refresh does (with a configured
  `token_endpoint` alone standing in for both endpoints, since discovery's
  config path wants both), takes the client from `Registrar.configured`
  (validation guarantees a `client_id`), builds the form with the grant's
  `unattendedGrant`, adds `resource` when the resource indicator is on, and
  sends it through `Broker.oauthClient` and `oauthClient.exchange`, over the
  connector's HTTP client (`Broker.httpFor`), which its discovery uses too. A
  refresh token in the answer is dropped. Scopes: a step-up's set, else the set
  the held token was granted for, else config `scopes`, else the challenge's
  scope, else none; never PRM `scopes_supported`. A 403 `insufficient_scope`
  runs the grant once with the union of the requested scopes and the
  challenge's, and the request is replayed once; a challenge that adds nothing
  to what was asked for fails `scope_denied` without a grant, and a 403 to the
  replay is `scope_denied` too, so a step-up cannot loop. A 401 to a token fresh
  from the grant is `grant_rejected`. The one translation of the token
  endpoint's refusal is in `unattendedTokens`: a needs_auth error from
  `exchange`, and `unauthorized_client`, become `grant_rejected` (config,
  provider code kept); `client_rejected`, transient, and other config errors
  pass through. `kindOf` stays one Case, one Kind. The jwt-bearer assertion is
  obtained for every grant and never kept: `assertion.file` is read again
  (missing or empty is `unresolved_value`), `assertion.value` resolved again,
  and `assertion.subject` signed with the signing key (`iss` the client ID,
  `sub` the subject, `aud` per `signing_key.audience`, a fresh `jti`, `exp` 60
  seconds after `iat`, header `typ` `JWT`). A refusal is final: no retry with
  the same assertion and no fallback grant. `Flows.Start` and the auth link's
  pages refuse an unattended connector as `not_interactive` (request); `Health`
  is zero for one; `Revoke` forgets its in-memory entry (which exists once the
  grant has run, even when it failed), reports a change, and so retries the
  grant, besides deleting any row a hand edit left from an auth flow. That
  revoke is the advised retry for a sticky `auth_error` after a fix at the
  provider.
- **Client authentication of a `jwt_bearer` connector.** Its signing key belongs
  to the assertion. `Registrar.configured`, which builds the `Registration`
  `chooseClientAuth` reads, is the one place this is decided: for `jwt_bearer`
  the key goes to `Registration.AssertionKey`, and to `Registration.SigningKey`
  (a client credential) only when
  `token_endpoint_auth_method = "private_key_jwt"`. So with no explicit method
  the client authenticates with its secret if it has one, else as `none` with
  its `client_id`, and never sends a `private_key_jwt` client assertion just
  because a signing key is configured. The grant itself has no special case.
- **Flows.** `auth.Flows` is the one entry to the flow for both doors
  (wayfindr-zgp.23): the browser's pages are built on it, and the daemon adapts
  it to `admin.Flows`, converting types only. `Start(ctx, name)` looks the
  connector up in the running config (through the lookup the daemon passes; the
  broker itself still keeps no copy and has no lookup, and neither has the
  Transport), checks that it uses OAuth, and starts the flow. A name the config
  doesn't have is `unknown_connector`, and a connector without an `[auth]` table
  of type `oauth` is `not_oauth`, both of Kind `request`; `Advise` words them,
  so no door writes its own advice. `HTTPStatus(err)` is the one mapping from a
  flow that cannot start to the status both doors answer: `request` 404;
  `needs_auth` and `config` 409; `unreachable` and `malformed` 502; `internal`,
  and any error that is not an auth error, 500. The flow enters the flow table
  as starting at the beginning of `Start`, with no state yet, so no callback
  finds it; it is armed (indexed by its state) only once it has its authorize
  URL, and a flow ended meanwhile is not armed. It probes the connector's URL:
  one unauthenticated GET, and, if that is answered 405 (a Streamable HTTP
  server with no SSE stream), one unauthenticated POST of a minimal `initialize`
  (wayfindr-zgp.11). If that is answered with an `Mcp-Session-Id` (a server that
  needs no token may open a session), the probe ends it with an unauthenticated
  DELETE, best-effort (wayfindr-zgp.24). One helper sends every probe. It keeps
  a 401's `WWW-Authenticate` as the challenge, then runs discovery with every
  document fetched again (a flow is the user's answer to an auth failure). PKCE
  follows ADR 0007: a connector without `client_id` needs
  `code_challenge_methods_supported` to list `S256`, or `Start` fails with
  `pkce_unsupported` (checked before registering, so no DCR client is made for a
  flow that cannot run; the Transport applies the same rule, one predicate, so
  the connector is already in `auth_error`, see below). A legacy server with no
  metadata (the 2025-03-26 default endpoints) passes (wayfindr-zgp.24): it has
  nowhere to advertise PKCE, so S256 is unknown, not unsupported, and the flow
  sends S256 anyway, which a server that ignores PKCE ignores; only metadata
  whose `code_challenge_methods_supported` lacks `S256`, or endpoints from
  config with no metadata at all, are `pkce_unsupported`. A manual connector
  uses S256 unless `pkce = false`, and even then if its `client_secret` resolved
  empty. The client comes from the Registrar's `obtain`, single-flight per
  connector (concurrent flows share one DCR registration). The effective
  redirect URI (`redirect_uri`, else `http://<listen>/oauth/callback`) is the
  one DCR registers and the authorize and token requests send. Scopes are the
  challenge's `scope`, else PRM `scopes_supported`, else config, plus the
  `requested_scopes` a step-up added. It adds `resource` unless that is
  disabled. `state` is 32 random bytes, and the flow is held in memory, indexed
  by the state's SHA-256, for a 10-minute TTL on the broker's clock; an ended or
  expired flow stays readable by `Wait` for another TTL, and is dropped on the
  next `Start` after that.
- **`HandleCallback`** (`Flows`, at `auth.CallbackPath`) looks up `state` and
  consumes it so it can only be used once (a replay gets a 400 page); a flow
  past its TTL ends as expired (`flow_expired`), and one the config rule
  outdates ends as `flow_cancelled` before any code is exchanged. It checks
  `iss` against the metadata's issuer (RFC 9207), and requires it when the
  metadata advertises `authorization_response_iss_parameter_supported`, unless
  `validate_issuer = false`, which logs the skip; a failure is
  `callback_issuer_mismatch` (needs_auth, not the discovery-time
  `issuer_mismatch`) and the code is not exchanged. Its advice warns of a
  possible mix-up attack, says to start the flow again and to report it if it
  recurs, and never suggests turning the check off. An `error` parameter ends
  the flow as `authorization_denied` with the provider code. It then exchanges
  the code through `oauthClient.exchange` (grant `authorization_code`, with
  `code`, `redirect_uri`, `code_verifier`, and `resource`), so the client
  authentication, the bounded read, and the Inspector chain are the refresh's; a
  stored or new DCR client the token endpoint rejects is forgotten as on refresh
  (`registration_expired`). It seals and stores the token through `storeGrant`
  (which fires `OnCredentialChanged`), bound to the resource, with the granted
  scope (the requested one when the response has none), completes the flow, and
  renders a "You can close this tab" page. Every page is `html/template`, with
  `frame-ancestors 'none'`, `X-Frame-Options: DENY`,
  `Referrer-Policy: no-referrer` (the callback URL holds the code), and
  `Cache-Control: no-store`. The "Continue" page alone is `same-origin`: under
  `no-referrer` a browser posts its form with `Origin: null`, which httpd
  refuses.
- **`Pages`** serve `/auth/{connector}` ([§7.7](7.7-httpd.md)), on `Flows`.
  `Confirm` renders the "Continue" form with a single-use nonce (32 random
  bytes, bound to the connector, expiring with the flow TTL, at most 1024
  unspent). `Start` spends the nonce (a missing, spent, expired, or other
  connector's nonce is a 403 page with the auth link, and starts nothing), calls
  `Flows.Start`, and answers 302 to the authorize URL, or a page with the
  error's advice and the status `HTTPStatus` gives it, the same status and
  advice the admin API answers. An unknown or non-OAuth connector is a 404 page
  with its advice. The callback's failure pages stay 400.
- **`Transport` RoundTripper:**
  1. Read the token (cached in memory, falling back to the store). If it is
     missing, return a needs-auth error (`no_credential`) without sending the
     request. For a connector without `client_id`, first apply the flow's PKCE
     rule (ADR 0007): run discovery as a flow would (the probe's challenge,
     cached documents), but with the cached challenge, so a connector that keeps
     reconnecting probes once per discovery, not once per connect
     (wayfindr-zgp.20), and if the rule fails return the config error
     `pkce_unsupported` instead, so the connector is `auth_error` rather than
     `needs_auth` with a link whose flow always fails. If that discovery fails,
     the error stays `no_credential`. A token bound to another url is
     `url_changed` (needs auth), and is never sent. For a connector without
     `client_id` the same rule applies to the new url (wayfindr-zgp.21), so
     `no_credential` and `url_changed` agree (wayfindr-zgp.24): metadata without
     S256 is `pkce_unsupported` (`auth_error`), since the link's flow would
     fail; a legacy server with no metadata, or a url that moved to a server
     with no OAuth at all, passes as above, and the error stays `no_credential`
     or `url_changed`.
  2. If `expiry - 60s < now`, refresh through `singleflight` keyed by
     `user_id|connector`. Waiters share the winner's result. The new token is
     sealed and stored before anyone is released.
  3. Send the request with `Authorization: Bearer`.
  4. On a **401**: force one refresh (single-flight), replay the request once
     using `req.GetBody`, and if the second response is also 401, return a
     needs-auth error (`token_rejected`).
  5. On a **403 with `error="insufficient_scope"`**: merge the scopes from
     `WWW-Authenticate` into `requested_scopes` and return a needs-auth error
     (`step_up`).
  6. Every token response goes through the per-provider inspectors (GLOSSARY:
     Inspector) first. A rejected grant (`invalid_grant` and its aliases) or an
     unknown provider code needs auth; a rejected client (`invalid_client` and
     its aliases) is a config error when it is the config `client_id`, but when
     it is a stored DCR client the client is cleared from the credentials row
     and the connector needs auth (`registration_expired`), so the next auth
     flow registers anew; a known transient code (`temporarily_unavailable`,
     `server_error`, `service_unavailable`, `rate_limited`, `ratelimited`) is
     `unreachable` and retried, not re-authorized. The upstream's own network
     errors are returned unchanged, which the manager treats as `unreachable`.
- **Errors** follow the seam-error convention (CODING_STANDARDS: Errors). Every
  error `auth` returns is an
  `*Error{Kind, Case, Connector, Link, ProviderCode, Detail, Err}`, narrowed
  with `AsError`; `Advise` turns one into `Advice{Summary, Action, Link}`. Each
  `Case` belongs to one `Kind`:
  - `needs_auth`: `no_credential`, `url_changed`, `client_changed`,
    `authorization_server_changed`, `credential_unreadable`, `refresh_failed`,
    `token_revoked`, `provider_error`, `token_rejected`, `step_up`,
    `registration_expired`, `authorization_denied`, `flow_expired`,
    `flow_cancelled`, `callback_issuer_mismatch` (the last four end an auth flow
    only), `authorization_pending` (a device code poll only; it never ends a
    flow). `Link` is `http://<listen>/auth/<connector>`, the page that starts
    the auth flow.
  - `config` (auth_error): `client_rejected`, `issuer_mismatch`,
    `pkce_unsupported`, `device_unsupported`, `no_registration`,
    `registration_rejected`, `unresolved_value`, `invalid_url`,
    `no_authorization_server`, `no_metadata`, `auth_method_unsupported`,
    `signing_key_invalid`.
  - `unreachable`: `transport` (the authorization server could not be reached),
    `provider_unavailable` (it answered a known transient code), `slow_down` (a
    device code poll only; it never ends a flow).
  - `malformed`: `malformed_response`, `unexpected_status`.
  - `internal`: `store`, `not_replayable`.
  - `request`: `unknown_connector`, `not_oauth` (only `Flows` returns them: the
    flow was asked for a connector it cannot authorize).

  `ProviderCode` is the sanitised code the authorization server sent. The
  caller's own cancellation and the upstream's transport errors are not auth
  errors and pass through unchanged. Because `upstream` may not import `auth`
  ([§2](2-package-map.md)), it matches by behaviour, through `errors.As`, which
  also sees through net/http's `*url.Error`: every auth error has
  `AuthCase() string` (the Case) and `AuthConfig() bool` (true for `config`),
  and only `needs_auth` errors have `NeedsAuth() (link string, stepUp bool)`.

- **Logging** records the connector, issuer, grant type, and outcome. Tokens,
  codes, verifiers, and secrets are never logged.
