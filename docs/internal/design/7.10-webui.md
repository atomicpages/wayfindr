# §7.10 `webui`

Part of the [Wayfindr technical design](../design.md). Go code cites this file
as "design §7.10".

The web console under `/ui/` (ADR 0016; adding connectors, ADR 0017).
`webui.New(Options)` returns one `http.Handler` that routes every `/ui/` path on
its own stdlib mux, and `httpd` mounts it as `Handlers.UI`: `GET /ui/` behind
the loopback Host and Origin guards, `POST /ui/` also behind the exact
same-origin `Origin` check ([§7.7](7.7-httpd.md)). Everything the console shows
or does goes through `webui.Admin`, the part of `admin.Client` it calls. The
daemon passes `admin.NewLocalClient(adminHandler)`, whose transport calls the
admin handler in process (no socket, no bearer, since httpd's guards are not in
the way), so the console and the CLI read the same JSON contract.

## Routes

| Route                                 | Does                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /ui/static/…`                    | Embedded assets (`static/`): CSS, htmx, `login.js`, `console.js`, fonts. `Cache-Control: no-cache`.                                                                                                                                                                                                                                     |
| `GET /ui/login`                       | The login page. Its script posts the code from the fragment. With a live session, 303 to `/ui/`.                                                                                                                                                                                                                                        |
| `POST /ui/login`                      | Spends the code; on success sets the cookie and 303s to `/ui/`, else 401 with the login page.                                                                                                                                                                                                                                           |
| `GET /ui/`                            | Connectors: `Status`, ordered error, warn, starting, ready.                                                                                                                                                                                                                                                                             |
| `GET /ui/connectors/{name}`           | One connector: its row and `Tools(name)`; a listing error shows its message in place.                                                                                                                                                                                                                                                   |
| `POST /ui/connectors/{name}/sign-in`  | `StartAuth`, then 303 to the authorize URL (http or https only), or, for a device code flow, a page with the user code and a link to the verification URI (http or https only). The form opens a new tab.                                                                                                                               |
| `POST /ui/connectors/{name}/sign-out` | `Revoke`, then 303 back with a toast.                                                                                                                                                                                                                                                                                                   |
| `GET /ui/calls`                       | `Calls` (`?connector=`, `?result=failed`), 100 newest. A row with error text puts its result in a `<details>`; opening it shows the text in a full-width row under it (CSS `:has()`, no script).                                                                                                                                        |
| `GET /ui/search`                      | `Search` with `explain` for `?q=`, 10 results.                                                                                                                                                                                                                                                                                          |
| `GET /ui/tokens`, `POST /ui/tokens`   | `ListTokens`; `CreateToken` renders the page with the value (never a redirect).                                                                                                                                                                                                                                                         |
| `POST /ui/tokens/{name}/revoke`       | `RevokeToken`, then 303 with a toast. The form's `return=cloud-agents` field sends the 303 to `/ui/cloud-agents` instead of `/ui/tokens`; any other value of `return` is ignored.                                                                                                                                                       |
| `GET /ui/cloud-agents`                | The Cloud agents wizard (ADR 0021). The stage comes from `?step=&agent=&connector=`, which hold the agent and connector names and never a secret, so a reload or back lands on the same stage. Lists the remote tokens (`ListTokens`).                                                                                                  |
| `POST /ui/cloud-agents/url`           | `SetPublicURL` (skipped when unchanged), then 303 to the token step; a refusal re-renders step 3 with its status.                                                                                                                                                                                                                       |
| `POST /ui/cloud-agents/token`         | `CreateToken` with `remote` set. Renders the done page, never a redirect: the token value, the connection test (step 5), and the agent's setup text (step 6) all need the value, which only this answer holds. If the status or the token list cannot be read here, the page is still rendered, without them, so the token is not lost. |
| `POST /ui/cloud-agents/test`          | `TestRemote` with the token from the form's hidden `token` field (the only place it travels, since Wayfindr kept only its hash); renders the done page again with the result.                                                                                                                                                           |
| `GET` of the three POST paths above   | 303 to `/ui/cloud-agents`: a browser without htmx can land on a POST path through its history. With htmx, the renders send `HX-Push-Url: false`, so the address bar stays on the step's GET URL and a reload or back is not a 404.                                                                                                      |
| `GET /ui/add`                         | The add form: a URL or a command connector.                                                                                                                                                                                                                                                                                             |
| `POST /ui/add`                        | A URL connector: `AddConnector`, then 303 to its page with a toast. A command connector: kept as a pending add, and the review page rendered; nothing is added. A refusal re-renders the form with its status, secret values dropped.                                                                                                   |
| `POST /ui/add/confirm`                | Takes the pending add by its token and `AddConnector`s it. A missing, spent, expired, or other session's token is 403.                                                                                                                                                                                                                  |
| `POST /ui/add/back`                   | Takes the pending add and shows the form filled from it, secret values dropped.                                                                                                                                                                                                                                                         |
| `GET /ui/oauth/approve?req=<id>`      | The approve page for a pending authorization of Wayfindr's authorization server (ADR 0022): claims it (`OAuthRequest`, which consumes the arm and drops every other pending authorization; a reload claims the same id again with no other effect), then shows the client, when it started, the IP "reported by your tunnel" (the last `X-Forwarded-For` entry; shown, never trusted), and a fixed warning to deny a link someone sent or a tab the user didn't open. When more than one request arrived during the arm (`arrived` above one), it shows instead that only one was expected and offers only Deny: the server refuses the approve (409). Without a session, or when the browser says the request is not a top-level navigation (`Sec-Fetch-Mode` other than `navigate`, `Sec-Fetch-Dest` other than `document`, or a prefetch or prerender `Sec-Purpose`, whenever sent, or `Sec-Fetch-Site` other than absent, `same-origin`, or `none`, so a page on another loopback port, which is same-site, cannot make the browser claim; an htmx fetch is one): a standalone page (`continue.html`, no sidebar, no admin call) with a "Continue" link to the same URL, a line to continue only after selecting Connect in an app and to close a tab the user didn't open, and how to sign in, never the login redirect, and it claims nothing. The name field, the connector picker (`picker` template, shared with the wizard), and the fixed warning are on the page; the IP line is left out when none was reported. See [§7.11](7.11-oauthserver.md). |
| `POST /ui/oauth/approve`, `/deny`     | `ApproveOAuth` or `DenyOAuth`, then 303 to the client's `redirect_uri` with the code or error (the forms opt out of boosting). A taken (409) or bad (400) name or connector list re-renders the page with the status, the request still claimed, as does a contested request's 409, with the page's own words for it; an unknown one (404) is the "expired or already answered" page. The 303 carries `Referrer-Policy: no-referrer` and `Cache-Control: no-store`, and its address, which holds the code, is neither logged nor shown; a return address that is not http or https is a 502.                                                                                                                                                                 |
| `GET /ui/oauth/deny`                  | 303 to `/ui/`.                                                                                                                                                                                                                                                                                                                          |
| `POST /ui/cloud-agents/oauth`         | `SetOAuthEnabled` for the ChatGPT path of the wizard (turning it on also arms the authorization server), then renders its done step.                                                                                                                                                                                                   |
| `POST /ui/cloud-agents/arm`           | `ArmOAuth` ("Connect a client"): Wayfindr's authorization server keeps authorization requests pending for the next 10 minutes, until the user's approve page claims one. Renders the ChatGPT done step with the arm's end time. The button is on that step and on the ChatGPT row of the first step while OAuth is on (a `form="arm-form"` button, since the row sits in the agent form). A 409 (OAuth off) renders the OAuth step, which turns it on, with the message.                                                                     |
| `GET /ui/cloud-agents/arm`            | 303 to `/ui/cloud-agents`.                                                                                                                                                                                                                                                                                                              |
| `GET /ui/cloud-agents/oauth`          | 303 to `/ui/cloud-agents`, as for the wizard's other POST paths.                                                                                                                                                                                                                                                                        |
| `POST /ui/cloud-agents/test`, no token | With `agent=chatgpt` and no `token`: `TestRemoteOAuth`, then the ChatGPT done step with the result. Any other agent without a token is a 400, as before.                                                                                                                                                                               |

Every other `/ui/` path is the 404 page. Every page but the login page and the
OAuth approve page's `GET` needs a session; without one it is a 303 to the
login page, or, for an htmx request, `HX-Redirect`. The approve page can't
redirect: the browser first arrives there from another site, so the
`SameSite=Strict` cookie is not sent even when the user is signed in, and the
login's redirect would lose the request id. The page without a session must not
claim the request: only the signed-in `GET` after Continue does, so a site that
sends the user's browser to the approve page with a stranger's id claims
nothing until the user selects Continue. The Continue page can't tell who
opened the tab, so it says to continue only after selecting Connect in an app;
and if the user continues anyway, a stranger's request is approvable only when
it was the only one to arrive during the arm, since the user's own arrives too
and makes two ([§7.11](7.11-oauthserver.md), One request per arm). The wizard's ChatGPT path (public
URL, turn OAuth on, the ChatGPT form values, the OAuth connection test) is in
[§7.11](7.11-oauthserver.md).

## Sessions

`webui.Sessions` holds login codes (`rand.Text`, 60s, at most 16) and sessions
(ID and CSRF token from `rand.Text`, 12h idle, at most 64), in memory, behind a
mutex; past either bound the oldest goes. A session also holds its pending adds
(ADR 0017): command connectors waiting for their confirm, by a `rand.Text`
token, each kept 5 minutes (`PendingTTL`), at most 4 per session. `take` spends
a token whether or not it is still valid, and the spec it holds, secret values
included, never leaves the daemon's memory. `admin.Options.UILogin` is
`Sessions.IssueLogin` adapted by the daemon, since `admin` cannot import `webui`
(§2). The cookie is `wayfindr_ui`, `Path=/ui`, `HttpOnly`, `SameSite=Strict`,
with no `Secure` (plain http on loopback) and no expiry.

Each form handler (`authedForm`) parses at most 16 KiB and compares the form's
`csrf` with the session's in constant time; a mismatch is 403.

## Rendering

Each page is its own template set, `layout.html` plus the page file, so every
page defines `content`. `render` executes into a buffer before writing, so a
template error is a 500, never half a page. View models are built in Go;
templates only lay them out. Template funcs: `code` (backtick spans to `<code>`,
every part escaped), `icon` (a sprite `<use>`), `logo` (`brandIndex.logo`).

The CSP is
`default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' https://cdn.jsdelivr.net; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'`,
so templates carry no inline `style` or script (the search score bar uses
`w-0`..`w-100` classes in steps of 5). It has no `form-action`: the sign-in
answer redirects to the authorization server, which Chrome checks against it.
`Referrer-Policy` is `same-origin`, not `no-referrer`, since under `no-referrer`
a browser sends `Origin: null` on a form post. That includes the approve page, which
holds a form: its policy stays `same-origin`, which already sends no Referer to
another site. The one hop that leaves the console, the 303 of the approve and deny
posts to the client, answers `Referrer-Policy: no-referrer`, which the browser
applies to the redirected request.

htmx 2.0.4 is configured by a meta tag (`allowEval: false`,
`includeIndicatorStyles: false`, `selfRequestsOnly: true`,
`historyCacheSize: 0`, and `responseHandling` that swaps every 2xx to 5xx answer
but 204, since htmx swaps no error answer by default and a refused form is a 400
or 409 page). `hx-boost` on `<body>` turns links and forms into swaps; the
connectors table polls `GET /ui/` every 10 seconds and selects itself
(`hx-select`), and the calls filters submit on change. The sign-in form opts out
of boosting (`hx-boost="false"`, `target="_blank"`). The server renders whole
pages only; htmx picks the part it swaps.

Logos come from theSVG through jsDelivr, pinned to one commit (ADR 0019). The
daemon embeds only that commit's slug list (`brands.gz`, refreshed with
`make brands` from `scripts/brand-index`) and matches a connector's name against
it: the whole name, then with trailing `-parts` dropped, after `aliases`
(`postgres` is `postgresql`). A match renders `default.svg`, with the brand's
`dark.svg` as a `prefers-color-scheme: dark` `<source>` when it has one, over
the connector's first letter. `console.js` (loaded in `<head>` without `defer`,
so its capture-phase `error` listener precedes every `<img>`) hides a logo that
fails to load, which shows the letter.
