# §7.1 `secrets`

Part of the [Wayfindr technical design](../design.md). Go code cites this file
as "design §7.1".

- **Key sources, in order.** `WAYFINDR_SECRET_KEY` (base64, 32 bytes); then the
  OS keychain (service `wayfindr`, account `master-key`); then
  `<data>/master.key` (mode 0600, with a warning logged when it is used). If
  none is available, the daemon refuses to start with an error naming all three
  options. `init` creates the key in the first writable source among keychain
  and file. It never generates a key when ciphertext already exists, because a
  new key would make that ciphertext unreadable.
- **`Sealer.Seal(plaintext, aad)`** returns
  `0x01 ‖ nonce(12) ‖ AES-256-GCM(ciphertext ‖ tag)`. `Open` rejects any other
  version byte. Callers pass `aad = "wayfindr/v1|<table>|<user_id>|<key…>"`, so
  a ciphertext copied into another row fails to open. A user secret uses
  `wayfindr/v1|secrets|<user_id>|<name>`, which only `resolve` builds: its
  `PutSecret` seals with it (`wayfindr secret set`, through the admin API) and
  `Resolve` opens with it. `resolve` reports a secret that won't open as
  `config.ErrUnreadable` (the `secrets` sentinel stays in the chain), and a
  missing one as `config.ErrNotFound`.
