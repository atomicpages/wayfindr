# §7.8 `daemon`

Part of the [Wayfindr technical design](../design.md). Go code cites this file
as "design §7.8".

1. **Startup.** `daemon.New` loads the config, takes the daemon lock
   (`daemonlock.Acquire` on `<data>/daemon.lock`, writing its pid and
   `server.listen` into the file), and binds the listener. If another daemon
   holds the lock, it exits with "daemon already running at `<listen>` (pid N)",
   adding that the daemon must be restarted to apply a changed `server.listen`
   when the two differ; if the port is taken by something else, it exits with
   "daemon already running?". The lock is an advisory OS lock (`flock` on Unix,
   `LockFileEx` on one byte far past the content on Windows, where byte-range
   locks are mandatory), so the OS drops it when the daemon exits, crashed or
   not, and it is never stale. It is the one-daemon-per-data-directory guarantee
   that ADR 0003 and 0004 rely on: the bind check alone misses a daemon started
   after `server.listen` changed. The lock and the bind come before the store,
   so a second daemon never runs migrations against the store a running one
   writes ([§9](9-security.md)); `Serve` releases the lock last, after the store
   has closed. `Acquire` retries a held lock for 250ms, since the shim's probe
   holds it for a moment. It then opens the store and runs migrations, calls
   `EnsureUser`, loads the master key (`secrets.Load`, which never creates one),
   and reads the client token. It builds the recovery module (step 5), the
   broker, manager, syncer (with no embedder yet), and gateway, the auth links
   naming the bound address, and binds the recovery module to the manager, the
   syncer, and the broker. `Daemon.Serve` first drops the catalog of every
   connector that has tools in the store (`ToolCounts`) but is not in the
   config, with `syncer.Remove`: one removed while the daemon was stopped, which
   a diff from no config never reports as `Removed`. This runs before serving,
   so no request finds its tools; its credentials stay, and the status lists
   them as orphaned. `Serve` then starts the HTTP server and applies the config
   as a reload from no config (`config.Diff(nil, cfg)`), which adds every
   connector (they connect in parallel; each new session requests a sync) and,
   when `[embedding]` is present, sets the embedder, which starts the embedding
   pass. The config watcher is set up just before that apply, so an edit made
   while it connects is queued and reloaded right after it; the poll (step 3)
   starts after it.
2. **Reload.** fsnotify watches the config _directory_, not the file: editors
   save by writing a temp file and renaming it over the config, which replaces
   the inode, and a directory watch survives that. A config that is a symlink
   (stow, chezmoi, home-manager) is edited at its target, in another directory.
   The watcher does not watch that directory, which may be the Nix store, where
   kqueue would hold a descriptor per file; every 2s it stats
   `filepath.EvalSymlinks(config)` and compares path, size, and modification
   time with what it last saw (wayfindr-a2b0). That poll also sees a repointed
   link, which kqueue (macOS, BSD) raises no event for. Events on other files
   and mode-only changes are ignored; any other event on the config's name, or a
   change the poll finds, restarts a 250ms debounce timer, so a save's burst of
   events makes one reload. The reload `config.Load`s the file with
   `Daemon.LoadOptions()`. An invalid config (or a deleted file) is logged and
   recorded as the status `config_error`, and the last good config keeps
   running; the next valid save applies and clears it. The watcher stops,
   waiting for a reload it is running, before shutdown begins. The daemon's
   reload owns the one current `*config.Config` and calls `config.Diff` once per
   valid config; every consumer acts on that one `Changes` (the manager and the
   broker keep no copy to diff against). Roughly:
   `ch := config.Diff(d.cfg, next)`; `next` becomes the running config of the
   status and the auth flows; `flows.ConfigChanged()` (step 6); `manager.Apply`
   with just `ch.Removed`; `syncer.Remove` each removed connector;
   `manager.Apply` with the rest of `ch`; `syncer.SetEmbedder` if
   `ch.EmbeddingChanged`; the poll's schedule (step 3); `d.cfg = next`. Removals
   go first so a removed connector's tools leave search before `Apply` waits for
   the other connectors to connect, and `syncer.Remove` ignores shutdown's
   cancel, so the catalog of a removed connector never outlives it. This is
   `Daemon.Reload(ctx, next)`; the watcher loads with `Daemon.LoadOptions()`,
   the same options as startup.
   - `Removed`: `Manager.Apply` stops the connector, then `Syncer.Remove` drops
     its catalog and fences off any sync of it in flight
     ([§7.4](7.4-catalog.md)). Credentials are kept.
   - `URLChanged`: `needs_auth` if the connector `UsesOAuth()`; otherwise
     reconnect and sync.
   - `Changed`: reconnect and sync.
   - `EmbeddingChanged`: swap the embedder and run `EmbedPending`.
   - `RestartRequired`: log a warning.
3. **Polling.** Every HTTP connector (Streamable or SSE) in `ready` or
   `unreachable` is synced (`Syncer.Sync`) each `refresh_interval`, with ±10%
   jitter. Stdio connectors are skipped: a new child is a new session, which
   syncs. So are connectors in `starting`, `needs_auth`, and `auth_error`:
   recovery opens a new session, which syncs, and a poll would only repeat the
   failed connect. The state is read when the poll is due, from
   `Manager.Status`, not when it was scheduled. Polling an `unreachable`
   connector is its retry: `ListTools` reconnects first.
   - **Owner.** The poll lives in `daemon` (`poll.go`), as
     [§2](2-package-map.md) says: it needs the config (which connectors are
     HTTP, the interval), the manager's states, and the syncer, and only
     `daemon` sees all three; `catalog` may not import `upstream` or own the
     config. It reaches them through functions `daemon` passes in
     (`Manager.Status`, `Syncer.Sync`), and hears of every sync through
     `catalog.Options.OnSynced`.
   - **Schedule.** Each connector has its own due time. A reload that adds,
     changes, or turns a connector into an HTTP one makes it due one interval
     later, since its connect has just synced it; a changed `refresh_interval`
     re-times every connector from the reload; removed connectors, and ones
     turned stdio, leave the schedule; the rest keep theirs. After a poll, the
     next is due one interval after it finished. Due connectors are synced in
     parallel, and the next timer is armed once they all return.
   - **Clock and jitter.** `daemon.Options.Clock` (`Now`, `NewTimer`) and
     `Options.Jitter` (a draw in [0, 1), default `math/rand/v2.Float64`) are
     injected, so tests step through polls deterministically. Unhinted, the
     interval is `refresh_interval` × (0.9 + 0.2·draw).
   - **Cache hints (go-sdk v1.8.0).** The client-side `mcp.ListToolsResult`
     embeds `mcp.Cacheable`, whose exported `TTLMs` and `CacheScope` carry a
     page's `ttlMs` and `cacheScope`; the SDK decodes them at every protocol
     version (a v1.8 server sends them on 2025 responses too, `ttlMs: 0` by
     default). The `ClientSession.Tools` iterator yields only the tools and
     drops them, so `Manager.ListTools` pages with `ClientSession.ListTools`
     itself and records the smallest page's `ttlMs` as
     `ConnectorStatus.ToolsTTL` (0, absent, or negative: no hint; cleared when
     the connector is reconfigured). `cacheScope` is ignored: Wayfindr is the
     only client of each upstream session. At 2026-07-28 the SDK also keeps a
     per-session TTL cache, so a `ListTools` within the hint is answered from it
     without a request. A hint, when there is one, replaces `refresh_interval`
     for that connector, bounded to [1 minute, 24 hours]. The floor keeps a tiny
     or mistaken hint from turning the poll into a busy loop against the
     upstream and the store; the ceiling checks a connector that claims a long
     freshness at least daily, so a wrong hint can't leave its catalog stale for
     long. The jitter then only lengthens it, by up to 20% (hint × (1 +
     0.2·draw)): a poll before the hint runs out would be served from the SDK's
     cache. A hint takes effect from the sync that read it, whoever requested
     that sync: the syncer's `OnSynced`, which the daemon routes to the poll,
     has it compare the connector's `ToolsTTL` with the hint its due time was
     set from, and on a change the next poll is due one interval, from the new
     hint, after that sync. So a new connector, which the reload schedules
     before its connect's sync has read a hint, first polls when that hint runs
     out, not after `refresh_interval` (wayfindr-t08.6). The reload and the
     re-time read the hint under the poll's lock, so either order of the two
     gives the same schedule.
4. **Shutdown.** On SIGINT or SIGTERM (`daemon.Run`; `Serve` on its context
   ending), stop accepting connections and drain in-flight requests for up to
   10s (`httpd.Server.Shutdown`, [§7.7](7.7-httpd.md)). httpd then cancels the
   contexts of the requests still running, such as a long-lived stream or a
   secret set whose retry is connecting, and gives them 1s more to return;
   requests still running after that are logged, and shutdown goes on. The
   cancel reaches `/mcp` tool handlers too, at every protocol version: the
   gateway ends each handler's context with its request's
   ([§7.6](7.6-gateway.md) Cancellation; wayfindr-rs5r). The poll stops before
   all of this, with the config watcher: its context is cancelled and it waits
   for the `Sync` calls it made, which return at once (the syncs carry on in the
   syncer). The drain runs before shutdown takes the reload lock and marks the
   daemon closed: a connector add reloads under that lock, and its `Apply` can
   wait on connects for up to the connect timeout, so only the drain's cancel
   ends it (wayfindr-zqef). With the watcher and the poll stopped, no other
   reload starts meanwhile. The order after the drain is: the recovery module
   (step 5) closes,
   which cancels the reconnects that credential changes started in the
   background (so the callback request never waits on a connect) and waits for
   them; then `Syncer.Close`, which cancels the running syncs and waits for them
   for what is left of the 10s drain budget, at least 1s; then every upstream
   closes (`Manager.Close`, which kills stdio children; it must come after,
   since the SDK's session close waits for requests in flight, such as a sync's
   `tools/list`), with the same budget: what is left of the drain, at least 1s.
   When it ends, every url upstream request still in flight is halted, so a
   session `DELETE` the upstream never answers, or a lock one holds, no longer
   holds shutdown (wayfindr-t08.12; [§7.2](7.2-upstream.md) **Close**); then the
   call log and the token touches flush (steps 7 and 9); then the store. No
   goroutine the daemon started outlives `Serve`, with one exception: a sync
   whose lister ignores the cancellation past that budget is abandoned and
   logged, and shutdown goes on (wayfindr-t08.7). It can't write to the closed
   store: `Syncer.Close` returns only once no write can follow
   ([§7.4](7.4-catalog.md)). Until then a sync that ignores the cancellation
   held shutdown without bound, since the store had to outlive it.

5. **Recovery.** One unexported module, `recovery` (`daemon/recover.go`), owns
   what follows each "the user fixed it" event (wayfindr-t08.9):
   - `credentialChanged(connector)` is the broker's `OnCredentialChanged` and
     returns at once. In the background it runs `Manager.CredentialChanged`,
     then, when the connector is ready, `Syncer.Await`: the new session's
     `OnToolsChanged` has requested a sync by the time `CredentialChanged`
     returns ([§7.2](7.2-upstream.md)), so the recovery waits for that one and
     starts none (one `tools/list`, wayfindr-zgp.12). Each connector's latest
     recovery is recorded.
   - `wait(ctx, connector)` waits for that latest recovery. The auth flow's
     long-poll ([§7.7](7.7-httpd.md)) reports a done flow once the recovery its
     token started has settled, with the connector's status from it.
   - `secretChanged(ctx, name)` serves `PUT /admin/secrets/{name}` (through an
     adapter to admin's `Upstreams`): `Manager.SecretChanged`, then
     `Syncer.Await` for each retried connector that is ready, in parallel, so
     the set's rows show fresh tool counts. Before it, the adapter calls
     `Daemon.embeddingSecretSet`: when the running `[embedding]`'s `api_key`
     refers to the secret, the embedder is rebuilt as on a changed `[embedding]`
     (the key resolved again, `Syncer.SetEmbedder`, which starts the embedding
     pass, and the gateway's query embedder), wayfindr-9ydc. The builds have
     their own lock, not the reload's, so a secret set never waits for a
     Reload's connects or shutdown's drain; shutdown closes it after the
     recoveries, before the syncer.
   - `revoke(ctx, connector)` serves `DELETE /admin/credentials/{c}`. It closes
     the connector's session while the token still exists (`Manager.Drop`), so a
     stateful upstream's session `DELETE` carries it (wayfindr-zgp.13); then the
     broker deletes the credential, which starts a recovery that reconnects
     without a token, into `needs_auth`; the answer waits for it. Each connector
     has a turn that its background recovery holds while it runs, and that the
     revoke holds from before the drop until the credential is deleted, so a
     recovery already running finishes first (its session is the one dropped)
     and none, the revoke's own included, connects in between. A call or a poll
     racing the revoke doesn't either: the turn is the recovery module's, so for
     the same span the revoke also holds the connector in the manager
     (`Manager.Hold`, [§7.2](7.2-upstream.md)), and such a use waits there, then
     connects after the delete, without the token, into `needs_auth`. So every
     session opened with the token is closed with it (wayfindr-t08.10).

   The module is built before the broker, which takes `credentialChanged` as its
   hook, and is bound to the manager, the syncer, and the broker once they exist
   (`bind`): the one late binding in `daemon.New`. Nothing calls it before
   `Serve`. That is the only path from a fix to the connector's state.

6. **Flows of changed connectors.** A reload calls `Flows.ConfigChanged()` once
   the new config is the running one and before `Apply`; auth's one rule
   ([§7.3](7.3-auth.md)) cancels each pending flow whose connector was removed
   or whose `url` or `[auth]` table changed, so a late callback stores no token
   for a connector that is gone, bound to its old url, or granted under its old
   auth settings. The daemon picks no connectors itself (wayfindr-zgp.15).

7. **Call log** (`daemon/calllog.go`). The gateway hands every `call_tool` call
   to `callLog.Record` ([§7.6](7.6-gateway.md) Call recording), which never
   blocks: it queues the row (256 deep) and drops it when the queue is full,
   counting the drops into one log line. One writer stores the rows, each
   bounded by 1s, and prunes rows older than `calls.retention` at start and then
   every hour (`PruneCalls`, bounded by 10s; one that times out deletes nothing
   and the next tries again). A reload sets the retention; a shorter one takes
   effect at the next prune. A retention of 0 turns the log off: nothing is
   recorded or pruned. The writer is not stopped by the serve context, so calls
   that finish during the drain are still written; shutdown stops it after the
   manager closes, and it writes what is queued within 2s before the store
   closes.
8. **Health check** (`daemon/health.go`). Every 15 minutes (`warnCheck`) the
   daemon reads every configured connector's warnings: auth's for its credential
   (`Broker.Health`, read against the connector in the running config,
   [§7.3](7.3-auth.md)); `certificate_expiring` for a url connector, OAuth or
   not, whose `[tls]` client certificate expires within 7 days or has
   (`httpclient.CertificateExpiry`, read from the file at each check; urgent
   within a day); and upstream's `stuck` for a connector not ready for more than
   a day (`ConnectorStatus.NotReadySince`). It logs at warn only the ones new
   since the last check, once per transition, and notes not at all; a credential
   it can't read is logged as an error and keeps the warnings already logged for
   it. A check only reads: refresh stays lazy (ADR 0004). The same `health`
   serves the status rows (`admin.Health`) and the gateway's `warnings`
   (`urgent`: credential and certificate failures due within a day).
9. **Client tokens** (`daemon/tokens.go`). `daemon.New` loads every
   `client_tokens` row into a new `clienttoken.Registry` before httpd serves, so
   scoped tokens work from the first request. Admin's token routes go through
   `clientTokens`, which writes the store first and the registry second, so a
   failed write leaves the registry as it was. The registry records each scoped
   token's use (by digest, on the daemon's clock); the daemon drains those
   touches into `TouchClientTokens` every minute and once more at shutdown,
   before the store closes. A failed write is logged and dropped: it costs only
   some `last_used_at`s.
10. **Adding a connector** (`daemon/connectors.go`, ADR 0017). The admin API's
    `AddConnector` is a `connectorAdder`, which writes the config file the
    daemon loaded (`paths.ConfigFile`), one add at a time (a mutex). It mirrors
    `wayfindr connector add`: it maps the `admin.ConnectorSpec` to a
    `config.NewConnector` (secret values become `${secret:<connector>_<key>}`
    via `config.SecretNameFor`; a spec that mixes URL and command keys, names a
    key twice, or has an empty secret is a 400), checks it with
    `config.AppendConnector` before any network call (a `*ValidationError` is a
    400 listing the issues; a `*config.Error` a 409, worded for the console,
    since `config.Advise` is worded for the CLI), probes a URL connector with
    `auth.Probe` (10 s) when auth is left to detection and it has no headers,
    stores the secrets with the resolver's `PutSecret`, and writes with
    `newfile.Replace` against the bytes it read (`ErrChanged` is a 409; stored
    secrets are kept). It then calls `reloadFile` itself rather than waiting for
    the watcher, so its answer can report the new connector; the watcher's own
    reload that follows finds an empty `Diff`. `Manager.Apply` has connected the
    new connector by the time the reload returns; a ready one is held for its
    first sync (`recovery.awaitSync`) so its row has its tools. The adder is
    built before the `Daemon`, so `New` binds its reload last.
11. **Usage report** (`daemon/telemetry.go`, ADR 0020). `daemon.New` builds a
    `telemetry.Reporter`, off until a config apply calls
    `SetEnabled(telemetry.enabled)`; `Reload` applies it before `Manager.Apply`,
    which can wait long on connects, so turning telemetry off holds at once and
    calls during the startup apply count. The reporter is blocked, whatever the
    config says, when `DO_NOT_TRACK` is set (not empty or `0`), when the build
    is not a release (`Options.Version` like `v1.2.3[-pre]`, not `-dirty`, and
    `Options.Commit` hex), or when there is no endpoint (`telemetry.Endpoint`,
    overridden by `WAYFINDR_TELEMETRY_ENDPOINT`). While it is blocked or off it
    counts nothing and writes no install ID; turning it on starts a new window
    from zero. The gateway's `Calls` is `countedCalls`, which counts each call
    for the reporter and then hands it to the call log, so
    `calls.retention = 0s` doesn't zero the counts; `OnSearch` counts
    `search_tools` calls. `keepTelemetry` sends on the daemon's `Clock`: first 5
    to 60 minutes after `Serve` starts (`Options.Jitter`), then every 24 hours.
    Each `Send` reads the running config (`configState.current`), solves the
    proof-of-work, checks again that telemetry is on in the same window (it may
    have been turned off while solving), and POSTs within 10s, following no
    redirect; a failed send is a debug log line and its counts wait for the
    next. Shutdown stops the schedule with the poll and the health check, before
    the drain; it uses no store.
