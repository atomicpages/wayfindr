# §7.6 `gateway`

Part of the [Wayfindr technical design](../design.md). Go code cites this file
as "design §7.6".

- **Server.** One `mcp.Server` with exactly two tools, served by one
  `mcp.NewStreamableHTTPHandler(..., &StreamableHTTPOptions{Stateless: true})`.
  That handler serves 2025-06-18, 2025-11-25, and 2026-07-28 clients (ADR 0003,
  R1). The gateway doesn't restrict versions, so the SDK also accepts the older
  ones it knows (2025-03-26, 2024-11-05) and answers an unknown one with
  2025-11-25; only the three above are supported. The handler also sets
  `DisableLocalhostProtection`: httpd's host guard owns Host and DNS-rebinding
  checks (loopback name and port, forwarding headers, remote client tokens; ADR
  0021, design §7.7), so the gateway must only ever be served behind that guard.
- **Cancellation.** A handler's context ends with the HTTP request that carried
  it, at every protocol version: when the client gives up (closes the request),
  and at the daemon's hard stop, which cancels every request's context
  ([§7.7](7.7-httpd.md) Server lifecycle). The stateless handler connects each
  request's session on the request's context but hides its cancellation from
  handlers, and its `PropagateRequestCancellation` stops hiding it only from
  2026-07-28. So `Gateway.ServeHTTP` keeps the request's context as a context
  value, which does reach the handlers, and receiving middleware
  (`endWithRequest`) ends each handler's context when that one ends. The option
  is not set: the middleware covers every version alike. A catalog read that
  fails once the context has ended is `canceled`, not `internal`/`catalog`
  (`catalogError`), so `call_tool` logs it as `failed` with Kind `canceled`, as
  it does an upstream call cut short the same way.
- **Request body limit.** `MaxRequestBodyBytes` is set explicitly to 4 MiB
  (`maxRequestBody`); a larger body is 413 "request body exceeds 4194304 bytes"
  at every protocol version. The largest legitimate body is a `call_tool` whose
  arguments carry a document or a file for the upstream, so the cap is generous;
  it still bounds what one request makes the daemon buffer. 4 MiB is the SDK's
  default today; setting it keeps an SDK upgrade from changing it unnoticed.
- **Capabilities.** The server declares only `tools`, without `listChanged`, and
  no `logging` ([§7.7](7.7-httpd.md)). Receiving middleware
  (`toolsonly.Middleware`, shared with the shim) answers every request of a
  capability it doesn't declare (`prompts/*`, `resources/*`, `completion/*`)
  with JSON-RPC -32601 "method not found", as a server that never implemented
  them would; the SDK would otherwise serve empty prompt and resource lists.
  `initialize`, `ping`, `server/discover`, `subscriptions/listen`, and `tools/*`
  are served as usual. `logging/setLevel` is left to the SDK: a no-op before
  2026-07-28, a removed method (-32601) from 2026-07-28.
- **`search_tools`** (`internal/gateway/search.go`) has two modes. A **search**
  needs a non-blank `query`, and takes `page` (at least 1, default 1), `size` (1
  to 10, default 5; with `detail: "brief"`, 1 to 25, default 15), and
  `connectors`, every one of which must be configured for this request
  (`unknown_connector` otherwise, listing the ones that are). A **lookup** by
  `names` takes 1 to 10 non-blank qualified names (duplicates dropped, order
  kept) and nothing else: `query`, `page`, `size`, `connectors`, or
  `detail: "brief"` with it is `names_conflict`. Numbers decode as float64, so
  `5.0` is accepted as 5.

  A search of every connector is bounded in the store by the request's allowlist
  (§7.6 Request narrowing), so pages stay full. If an embedder is configured
  (`Options.Embedder`, with `Options.EmbedTimeout` from `embedding.timeout`),
  the query is embedded through the cache of [§7.5](7.5-search.md) and the
  vector and the embedder's model identity go in the `SearchQuery`; otherwise,
  or when embedding fails, the search is lexical-only. The daemon calls
  `Gateway.SetEmbedder` on `EmbeddingChanged`, as it does `Syncer.SetEmbedder`.
  What the store returns is filtered again (`dropHidden`) for the live tools
  list, the profile, and the scope file, so a page can come back short by the
  tools they hide.

  The response holds `tools` (each definition with `name` rewritten to the
  qualified name, or a brief entry: name, title, a summary of at most 160 runes,
  required argument names, annotations), `page`, `size`, `has_more`,
  `unavailable`, and `warnings`. `unavailable` lists the connectors in reach
  (narrowed, and limited to `connectors` when given) that are not `ready`, each
  `{connector, status}` plus `summary`, `action`, and `link` from
  `ConnectorStatus.Advice()` ([§7.2](7.2-upstream.md)), the advice
  `wayfindr status` shows; the gateway has no wording of its own for a state.
  `warnings` are the ready connectors' credential failures due within a day
  (`Options.Warnings`, served by the daemon's health, [§7.8](7.8-daemon.md) step
  8). A lookup also returns `missing`: each name that is not qualified, whose
  connector isn't configured for the request, that the catalog lacks, or that is
  hidden. A lookup that finds none is an error (`none_found`); when a named
  connector is not ready, its advice, link included, replaces the generic one.

- **`call_tool`** (`internal/gateway/call.go`). The handler, `callTool`, only
  maps the MCP request onto the one call path, `callCore`, which every door
  shares: a `CallRequest` (the qualified name, the arguments, and a `Resume`
  when the request answers an `input_required`) and `CallOptions` (the
  `clienttoken.Client`, the `clientInfo` name for the call log, `Narrow`, a
  closure over `narrowingOf`, and the `Asker`: the protocol version and
  capabilities `ask` checks). `Narrow` is required: a call without it is
  refused as `internal`/`no_client`, never served unnarrowed. `callCore` then:
  1. Split `name` at the first `.`. Connector names may not contain dots, so
     this is unambiguous. A missing or unqualified name is refused before the
     request is narrowed, so a bad name beats a bad profile header.
  2. Narrow the request (below), by calling `Narrow`. A connector the client
     token leaves out, or that isn't configured, is `no_connector`. A tool the
     tools list, the profile, or the scope file hides by name alone is refused
     before the catalog is read, so an out-of-scope call learns nothing about
     it.
  3. `GetTool`. A missing tool is `hidden_by_policy` if the tools list hides its
     name, or the last sync's hidden list ([§7.4](7.4-catalog.md)) has it and
     the live list still hides that class; else `not_in_catalog`, whose advice
     suggests `search_tools`.
  4. Check the entry's class against the live tools list, the profile, and the
     scope file (`hiddenBy`, in that order): the catalog can still hold a tool a
     reload just hid, until the re-sync.
  5. Compile the schema once per definition and cache it, keyed by the SHA-256
     of the full definition bytes (the content hash covers only names and
     descriptions, so it misses schema-only changes). Validation runs with
     `santhosh-tekuri/jsonschema/v6`: every `$ref` outside the schema (remote,
     relative, or `file:`) fails to load and `format` is an annotation only. If
     the schema fails to compile, log a warning once per definition and forward
     without validating. "Once" is per cache entry: the cache holds at most 1024
     definitions (`maxSchemas`) and is emptied when full rather than tracking
     recency, so a definition compiled again after a flush logs its warning
     again, as can two calls that race to compile a new definition.
  6. Call `Manager.Call`, or `Manager.Continue` when the request carries
     `requestState` or `inputResponses` (below), and return the upstream result
     unchanged, unless it asks for input.
  7. Measure the result (`resultBytes`): the `len` of its JSON encoding, which
     covers its content and `structuredContent`, for the call log
     ([Call recording](#call-recording)). Only a result that came back is
     measured: an `input_required` one is not, and neither is a refusal or a
     failure. An `isError` result is. This encodes the result a second time,
     after the SDK encodes it for the client, one marshal per call, which is
     accepted.
- **Other doors** (`internal/gateway/door.go`). `Call` is the exported entry
  to `callCore` for a door that is not `/mcp`: the admin API's
  `POST /admin/tools/call`, which the daemon adapts (`adminCall`,
  [§7.8](7.8-daemon.md)) for `wayfindr call` and the console's tool form. The
  daemon resolves the request's token as httpd's bearer guard does (the default
  token's digest in constant time, else `Registry.Lookup`; none is the default
  Client), narrows by `config.Narrowing{Token: client.Connectors}` alone (the
  owner has no profile and no scope file), and passes an `Asker` with
  `NewestProtocolVersion` and form and URL elicitation, since both callers
  answer either. Everything else is `callCore`'s: a hidden tool is refused, and
  the call log names the door's client (`wayfindr-cli` or `console`) and the
  token. `Class` reads a catalog entry's class by `toolClass`'s rule, for the
  admin answer; the admin API is the owner's alone, who sees every class in
  `connector tools` anyway.
- **Error rendering.** Every gateway-side failure is
  `CallToolResult{IsError: true, Content: [text]}`, never a JSON-RPC error. The
  gateway's own failures are `gateway.*Error{Kind, Case}` with `gateway.Advise`;
  `Manager.Call` failures render `upstream.Advise` of the `*upstream.Error`. The
  text is the advice: summary, `To fix: <action>`, and `Link: <url>` (the
  `needs_auth` link the error carries: its cause's, or the manager's
  `Options.AuthURL`). A failure that is neither is logged and rendered as a
  generic internal error.

## Request narrowing

Every `search_tools` and `call_tool` request is narrowed by one
`config.Narrowing` (`internal/config/scope.go`), which the gateway's
`narrowingOf` builds per request, in this order:

1. **Token.** The `clienttoken.Client` httpd resolved from the bearer
   ([§7.7](7.7-httpd.md)), read once with `clientOf`: nil connectors for the
   default token, else the scoped token's list. It is the outer limit and is set
   by the server, so the client can't widen it. A connector it leaves out is not
   configured as far as the request knows: `call_tool` refuses it as
   `no_connector`, `search_tools` refuses it in `connectors`, and it never shows
   in `unavailable` or `warnings`. A request with no Client is refused
   (`internal`/`no_client`): serving it would ignore the limit.
2. **Profile.** The name in `Wayfindr-Profile`, sent by the shim's `--profile`,
   or copied from `/mcp?profile=<name>` by `Gateway.ServeHTTP`. It is looked up
   in the running config (`Options.Profile`) on every request, so an edit
   applies from the next one. A name sent twice, an invalid name, or a query
   that doesn't parse is `invalid_scope`/`bad_profile`; an unknown name is
   `unknown_profile`.
3. **Scope file.** The JSON project scope in `Wayfindr-Scope`, which only the
   shim sends ([§3](3-paths.md)). One that doesn't parse, or comes twice, is
   `invalid_scope`. Trusting it is safe because it only narrows.
4. **Tools list.** The connector's own list from the running config
   (`Options.Policy`), checked separately, as it also filters the catalog.

A connector must pass the token, the profile, and the file; a tool must pass the
tools list, the profile's, and the file's. The refusal names the first that hid
it: `hidden_by_policy`, `hidden_by_profile` (with the profile's name, so its
advice can say where to allow it), or `hidden_by_scope`. The token never appears
as a source: to the client, a connector it excludes is simply not configured.
Every narrowing refusal is fail-closed, since serving the request unscoped would
widen it.

## input_required round trip

When `Manager.Call` or `Continue` returns a result with `InputRequests`
([§7.2](7.2-upstream.md) Elicitation), the gateway's `ask`
(`internal/gateway/input.go`) puts them to the client:

- Each request id becomes `<connector>-<id>` and each message is prefixed
  `<connector> asks:`, so the user sees who asks.
- The upstream's `RequestState` is wrapped in a sealed `requestState` (GLOSSARY:
  Request state): the client token's instance, the connector, the tool, a
  digest of the arguments that ignores key order and whitespace, an expiry of
  `upstream.InteractionTTL` (10 minutes) on the gateway's clock, and the
  upstream's state, sealed with the master key under the user's AAD, so the
  client can neither read nor forge it.
- The instance is `clienttoken.Client.Instance`: the token's name and, for a
  scoped token or an OAuth grant, its `CreatedAt` to the millisecond, which the
  daemon puts in the `Client` it registers (a grant's, not its rotating access
  token's). Revoking a token frees its name, so a token or grant created again
  under it within the state's lifetime is another instance. The default token's
  instance is its name. A `Client` with no instance (no name) matches no state.
- A client older than 2026-07-28 can't take `input_required` over the stateless
  `/mcp`: the call fails `cannot_ask`/`client_too_old`. A client whose
  capabilities lack elicitation (or the mode asked for) fails
  `cannot_ask`/`no_elicitation`. Either way the upstream's question is
  `Discard`ed, so the upstream isn't left waiting.

The client answers by calling `call_tool` again with the same name and
arguments, `requestState`, and `inputResponses`. `openState` checks that the
state is one this gateway sealed for this user, for a call made with this
client token instance, for this tool and these arguments, and not expired
(`invalid_request_state` otherwise; a state sealed before it carried a token
matches none); the answers are mapped back to the upstream's ids, and
`Manager.Continue` resumes the call. An answer refused before it reaches
`Continue` (a narrowing, validation, or request state refusal) discards the
question, but only when it came with the client token instance the state was
sealed for: another token's answer can't cancel the question, which waits for
its own client's answer or its expiry. The stdio shim does the same round trip
itself for an older stdio client, asking it with `elicitation/create`
([§7.9](7.9-cli.md)).

## Call recording

`callCore` records every `call_tool` call once, however it ended, through
`Options.Calls` (the daemon's call log, [§7.8](7.8-daemon.md) step 7), as a
`store.Call`: the time it arrived, the client's `clientInfo` name (the shim
forwards its own client's in `_meta`), the token name from the same Client the
narrowing used (`default` or the scoped token's), the connector and tool as the
agent wrote them (clipped and printable, [§5](5-data-model.md)), how long the
upstream took (connecting included; none when it was never called), and the
result: `ok`, `tool_error` (an `isError` result), `input_required`, `rejected`
(the gateway's own refusals, with their Kind and Case), or `failed` (`internal`,
`cannot_ask`, `canceled`, and every upstream error, with its Kind and Case). A
call that is not `ok` or `input_required` also records its error text (ADR 0014,
amended): the text contents of the upstream's `isError` result, or the rendered
advice `errorResult` returned. `errorText` joins the text on one line
(whitespace runs become one space), applies `redact.Printable` and
`redact.URLQueries`, and cuts it to 500 bytes on a rune boundary. `Record` never
blocks the call. The row also carries `ResultBytes`, the size from step 7
([§5](5-data-model.md)); nil when the call returned no result, or asked for
input.
