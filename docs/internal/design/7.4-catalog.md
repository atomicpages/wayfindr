# §7.4 `catalog`

Part of the [Wayfindr technical design](../design.md). Go code cites this file
as "design §7.4".

```go
type Syncer struct{ /* manager, store, embedder (nil-able) */ }
func (s *Syncer) Sync(ctx context.Context, connector string) error
func (s *Syncer) Request(ctx context.Context, connector string) // Sync in the background
func (s *Syncer) Await(ctx context.Context, connector string) error // wait for the requested sync; starts none
func (s *Syncer) Remove(ctx context.Context, connector string) error
func (s *Syncer) EmbedPending(ctx context.Context) error
func (s *Syncer) RequestEmbed(ctx context.Context)            // EmbedPending in the background
func (s *Syncer) SetEmbedder(ctx context.Context, e Embedder) // nil removes it; starts a pass
func (s *Syncer) Close(ctx context.Context) error
```

The Syncer owns the catalog's lifecycle. For syncing, the daemon wires two
things to it: `OnToolsChanged → Syncer.Request` ([§7.2](7.2-upstream.md)), which
syncs a connector on every new session and every `list_changed` (add, reconnect,
`Retry`, and recovery alike, on any transport), and, on a reload that removes a
connector, `Syncer.Remove` after `Manager.Apply` has dropped it. The daemon's
poll ([§7.8](7.8-daemon.md) step 3) calls `Sync` for each HTTP connector it
polls, and `Options.OnSynced`, called after every sync that wrote its catalog
(whoever requested it, before its `Sync` callers return), tells the poll to
re-time the connector from the cache hint that sync read (wayfindr-t08.6).
Shutdown closes the daemon's recovery module first ([§7.8](7.8-daemon.md) step
4), then `Syncer.Close(ctx)`, `Manager.Close(ctx)`, and the store: the SDK's
`ClientSession.Close` is graceful and waits for the requests in flight on the
session, so a sync still listing tools would hold the manager's close until the
connector timeout; `Syncer.Close` cancels it first, and a `Request` after it
does nothing.

`Close` is bounded by its `ctx` (wayfindr-t08.7). Every catalog write (a sync's
`ApplySync`, `Remove`'s `DeleteCatalog`, the embedding pass's `SetEmbeddings`)
runs in one write slot and checks there that `Close` has not begun, writing
nothing if it has. When `ctx` ends with runs still going, because a lister or
embedder ignores the cancellation, `Close` takes the slot once, which waits only
for a write already in progress (bounded: the cancel reaches it too), logs the
runs it abandons, and returns `ctx.Err()`. From then on no write can reach the
store, so the store may close whatever `Close` returned; an abandoned run that
returns later finds the Syncer closed and writes nothing. (A read, such as the
embedding pass's `PendingEmbeddings`, may still reach a closed store and fail;
that only ends the pass.)

- **Tools lists.** `Options.Policy` returns a connector's tools list from the
  running config. `fetch` (`internal/catalog/syncer.go`) splits the listed
  tools: those the list exposes become `store.Tool` values, and the rest go to
  `SyncOutcome.Hidden` as `{name, class}`, never into the catalog (a hidden tool
  also skips `store.NewTool`'s validation, so a malformed one can't fail the
  sync). `ApplySync` stores the hidden list in `connector_sync.hidden_tools`; a
  failed sync keeps the last success's. The gateway reads it to tell
  `hidden_by_policy` from `not_in_catalog` for a name no longer in the catalog
  ([§7.6](7.6-gateway.md)), and the status counts it (`hidden_tools`). A changed
  tools list is a `Changed` connector ([§4](4-configuration.md)), whose
  reconnect syncs again.
- **`Sync`** calls `ListTools`, builds `store.Tool` values, and stores the
  outcome with one `ApplySync`: the new catalog and its sync record on success;
  on failure only the record, whose error the Syncer has redacted with
  `internal/redact` ([§9](9-security.md)). The fetch also rejects a list that
  repeats a tool name, so that failure is recorded too rather than rejected by
  the store, which would write nothing. A successful sync then starts an
  embedding pass in the background, so a slow or failing provider never slows or
  fails a sync. At most one sync runs per connector at a time: a call that
  arrives while one is running is coalesced into a single rerun. A sync that
  fails with upstream's `unknown_connector` (the connector was removed) records
  nothing. `catalog` may not import `upstream`, so it matches by behaviour:
  upstream's `*Error` has `UpstreamKind() string`, which `catalog` finds with
  `errors.As` through a one-method local interface.
- **`Await`** waits for the sync of a connector already requested and starts
  none: the rerun queued behind a running sync, else the running one; with
  neither it returns nil at once. It returns that run's outcome. The daemon's
  recovery module ([§7.8](7.8-daemon.md) step 5) calls it once a reconnect has
  returned, by when the new session's `OnToolsChanged` has requested its sync
  ([§7.2](7.2-upstream.md)), so a recovered connector is reported with its tools
  after one `tools/list`, not two (wayfindr-zgp.12).
- **`Remove`** is a fence. It bumps the connector's generation, then, holding
  the Syncer's write slot, deletes its tools and its last sync in one
  `DeleteCatalog`; its credential stays. Each sync run carries the generation
  current when it was last requested, and checks it in the same write slot
  before `ApplySync`; a run from an older generation discards its result and its
  `Sync` callers get `ErrRemoved`. So a sync in flight or queued when `Remove`
  is called writes neither tools nor a sync record after it: no ghost tools.
  `Remove` abandons such a run rather than waiting for its fetch, and waits only
  for a write already in progress. The embedding pass needs no fence:
  `SetEmbeddings` skips a vector whose row no longer has the content hash it
  read, and a deleted row matches nothing. Re-adding the connector later syncs
  it on its first new session, in the new generation. The daemon calls `Remove`
  after `Manager.Apply`, so no new session can request a sync between the two; a
  sync that runs anyway fails `unknown_connector`.
- **Embed text** is built deterministically:
  `"<connector>.<name>\n<title>\n<description>\n"`, then one
  `"<param>: <param description>"` line per top-level `inputSchema.properties`
  key, in sorted order. `content_hash` is the sha256 of that text.
- **`EmbedPending`** embeds rows whose `embedding_model` differs from the
  current model identity, in batches of 64. Each batch has
  `Options.EmbedTimeout` (default `DefaultEmbedTimeout`, one minute), so a
  provider that takes the request and never answers fails the batch instead of
  stalling the pass, and every rerun queued behind it, until `Close`
  (wayfindr-gxnw). If a batch fails, it logs the failure and stops. The rows stay pending and remain lexically searchable, and
  the next sync retries them. One pass runs at a time; extra requests coalesce
  into one rerun, and `Close` cancels a running pass. The daemon calls
  `RequestEmbed` at startup and `SetEmbedder` on `EmbeddingChanged`, so changing
  the model re-embeds everything without blocking search. With no embedder
  configured, passes are no-ops.
